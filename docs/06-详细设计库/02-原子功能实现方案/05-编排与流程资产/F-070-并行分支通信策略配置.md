- 类型：用户可见功能

- MSABC 分类：S

## 2. 功能目标
- 节点与节点之间的协作必须支持显式配置：
  - 正式工件
  - 临时消息
  - 控制信号
- 并行分支必须支持多种通信模式：
  - 串行传递
  - 广播
  - 共享黑板
  - 汇合后消费
- 角色只定义协作纪律，不定义最终交付格式。
- 真正的通信规则必须由边绑定和节点 IO 决定。

## 5. 具体实现方案
### 前端/交互
- 边 Inspector 必须至少显示 3 个分区：
  - 工件绑定
  - 消息绑定
  - 控制信号绑定
- 每条边的通信配置项至少包括：
  - 上游输出对象
  - 下游输入对象
  - 作用域：本轮运行 / 持久工件
  - 生命周期：临时 / 持久
  - schema 校验
- 并行分支通信区必须支持模式预设：
  - `串行传递`
  - `广播`
  - `共享黑板`
  - `汇合后消费`
- 若边绑定失效，画布中的边必须显示错误态，且 Inspector 给出具体原因。

### 主进程/服务
- 主进程负责把 Flow 中的边转换成运行时通信图。
- 运行时通信图必须显式区分：
  - `artifactBindings`
  - `messageBindings`
  - `signalBindings`
- 并行分叉节点创建分支执行上下文。
- 并行汇合节点等待分支完成，并读取工件、消息和控制信号决定后续走向。
- 控制信号只用于流程控制，不得直接替代正式交付工件。

### 数据与持久化
- 边对象最小结构：
```json
{
  "sourceNodeId": "node-blue",
  "targetNodeId": "node-red",
  "artifactBindings": [],
  "messageBindings": [
    {
      "source": "runtime/blue_packet.json",
      "target": "inputMessages.blue_packet",
      "schema": "review-packet"
    }
  ],
  "signalBindings": [],
  "deliveryMode": "direct"
}
```
- 临时消息默认写入运行态目录，例如：
  - `runtime/messages/<run-id>/`
- 正式工件写入工件目录或输出目录。

### 校验与异常
- 校验上游输出对象是否存在。
- 校验下游输入对象是否存在。
- 校验消息 schema 是否匹配。
- 校验控制信号是否被目标节点支持。
- 若边绑定失效，不允许正式运行。
- 若并行汇合所需分支未全部满足，必须阻塞并显示缺失项。

## 6. 红蓝裁判例子
```text
蓝军 -> 红军
  消息绑定：
  - blue_packet.json => red.inputMessages.blue_packet

蓝军 -> 裁判
  工件绑定：
  - blue-draft.md => judge.inputArtifacts.blue_draft
  消息绑定：
  - blue_packet.json => judge.inputMessages.blue_packet

红军 -> 裁判
  工件绑定：
  - red-issues.md => judge.inputArtifacts.red_issues
  消息绑定：
  - red_packet.json => judge.inputMessages.red_packet

裁判 -> 循环节点
  信号绑定：
  - continue_review => loop.continue
```

这个例子里：

- 蓝军、红军、裁判三个角色都不定义最终输出文件树。
- 边绑定定义谁把什么给谁。
- 裁判的信号决定循环是否继续。

## 7. 自动测试
- 单元：
  - 边绑定解析
  - 消息 schema 校验
  - 控制信号校验
  - 并行依赖解析
- 集成/端到端：
  - 配置并行分支通信后运行 Flow，验证工件、消息和信号按预期传递
- 回归：
  - 边绑定失效
  - 分支失败
  - 消息缺失
  - 汇合等待超时

## 8. 用户模拟测试
1. 创建一个包含 2 个并行分支和 1 个汇合节点的 Flow。
2. 为分支配置消息绑定和工件绑定。
3. 运行后确认汇合节点能看到来自两个分支的输入。
4. 删除一个上游消息绑定，确认系统阻止运行并显示错误原因。
