# 编排层操作与工作方式

## 1. 文档目的
本文件用于回答 4 个问题：

1. 编排层在 Cyber Editor 中到底是什么。
2. 用户在界面上如何真正使用编排层。
3. 编排层如何定义输入、输出、角色、工件、导出和运行约束。
4. 一个具体 Flow 应该如何被搭建、调试、运行和交付。

本文件不是概念说明，而是实现说明。目标是让不了解背景的程序员或 AI 能据此实现编排层主链路。

## 2. 编排层的定位
Cyber Editor 是一个以编排层为核心的桌面图文工作台。

编排层不是“一个额外的高级页面”，而是产品的中心系统。它负责：

- 定义用户要做的工作流程。
- 定义输入目录、输出目录和工件目录。
- 定义节点之间如何流转。
- 定义每个节点读什么、写什么、需要谁来做。
- 定义阶段确认条件和导出条件。
- 定义最终交付物的目录结构和格式。

产品本身不固定输出结构。输出结构由“模板 + Flow + 工件契约 + 导出映射”共同决定。

## 3. 编排层中的核心对象
编排层必须明确区分以下对象。

### 3.1 Template
模板是“可复用的工作方式包”，用于给小白用户直接上手。

模板至少包含：

- 默认 Flow
- 默认 Subflow
- 默认角色包引用
- 默认工件目录
- 默认输入目录和输出目录
- 默认阶段输出契约
- 默认导出映射

例子：

- 软件工厂默认模板
- 视频脚本工作流
- 旅行攻略整理流

### 3.2 Flow
Flow 是一条完整主流程，是编排层中最核心的运行对象。

Flow 必须包含：

- 节点集合
- 边集合
- 节点画布位置
- 输入目录配置
- 输出目录配置
- 工件目录配置
- 阶段输出契约
- 导出映射
- 运行策略

### 3.3 Subflow
Subflow 是可复用的流程片段，用于把复杂逻辑抽离成单独组件。

例子：

- 红蓝裁判审查
- 方案评审子流程
- 导出交付包

Subflow 必须支持：

- 被主流程节点引用
- 独立打开编辑
- 独立保存
- 独立版本化

### 3.4 Role Package
角色不是一段 prompt 文本，而是一个目录化角色包。

角色包至少包含：

- `role.json`
- `IDENTITY.md`
- `SOUL.md`
- `AGENTS.md`
- `USER.md`
- `Skills/`
- `MEMORY/`
- `MEMORY/MEMORY.md`
- 可选 `schemas/`

角色负责：

- 目标
- 角色设定
- 人格与价值观
- 协作纪律
- 服务对象适配
- 可用技能集合
- 可用连接范围
- 可用工具范围
- 运行约束

角色不负责：

- 定义最终输出格式
- 定义输出目录
- 定义最终导出文件树

这些属于 Flow、节点 IO、阶段契约和导出映射。

### 3.5 Artifact
Artifact 是工件定义。工件是流程中的正式输入物、中间产出物或最终交付物。

支持的工件类型至少包括：

- Markdown 文档
- 表格工件：`csv`、`tsv`、`xlsx`
- 图工件：流程图、思维导图、框图
- 引用型工件：通过超链接或嵌入引用其他工件

### 3.6 Stage Contract
Stage Contract 定义某个阶段必须完成哪些工件，才能允许确认阶段。

例子：

- `发现` 阶段必须有“原始想法文档”
- `方案拆解` 阶段必须有“功能树”和“功能清单”
- `导出前` 阶段必须有“通过校验的目标工件”

### 3.7 Export Mapping
Export Mapping 定义正式交付时，哪些工件被导出到什么目录，以什么文件名和格式导出。

例子：

- `原始需求` -> `01-requirements/01-原始需求.md`
- `流程图` -> `02-solution/03-流程图.md`
- `交付摘要` -> `03-openspec/00-交付摘要.md`

### 3.8 Message / Signal Channel
在同一条 Flow 中，多个 Agent 不只通过正式工件沟通，还需要运行时消息通道和控制信号通道。

至少支持 3 类传递对象：

- 正式工件：用于持久化和交付
- 临时消息：用于 Agent 间协作，不一定进入最终交付
- 控制信号：用于条件、循环、并行汇合和人工确认

关键原则：

- 正式交付物格式由 Flow、节点 IO、阶段契约和导出映射决定。
- 角色可以定义“如何沟通”，不能定义“最终交付长什么样”。

## 4. 对象之间的关系
对象关系如下：

```text
Template
  ├─ default Flow
  ├─ default Subflows
  ├─ default Role Packages
  ├─ default Artifact Directory
  ├─ default Stage Contracts
  └─ default Export Mapping

Flow
  ├─ Nodes
  ├─ Edges
  ├─ Input Directories
  ├─ Output Directories
  ├─ Artifact Directory
  ├─ Stage Contracts
  ├─ Export Mapping
  └─ Runtime Policy

Node
  ├─ Node Type
  ├─ Node Position
  ├─ Input Artifacts
  ├─ Output Artifacts
  ├─ Input Messages
  ├─ Output Messages
  ├─ Output Signals
  ├─ Role Package Binding
  ├─ Skill Binding
  ├─ Connector Binding
  └─ Tool Binding
```

一个关键原则：

- 角色决定“谁做”
- 节点决定“做什么”
- 工件决定“读写什么”
- Flow 决定“按什么顺序做”
- 导出映射决定“最后交付成什么”
- 边决定“节点之间到底传什么”

## 5. 编排层的主使用方式
编排层必须同时支持两条主路径。

### 5.1 小白路径：直接使用流程
适用于不知道如何设计流程的用户。

操作顺序：

1. 在欢迎页点击“创建编排”或“新建工程”。
2. 进入模板选择界面。
3. 选择现成模板。
4. 查看模板说明、工件目录、输入输出目录和预计产物。
5. 直接运行模板，或只做少量修改。
6. 在运行视图中查看结果。
7. 满意后保存为自己的编排或绑定工程。

小白路径的设计要求：

- 默认隐藏复杂设置。
- 默认显示模板说明、输入输出目录和预期结果。
- 默认显示“下一步做什么”。
- 高级设置必须进入 Inspector 高级区，而不是首屏展开。

### 5.2 高手路径：自己设计流程
适用于知道自己要怎么拆流程、角色和工件的用户。

操作顺序：

1. 在欢迎页点击“创建编排”。
2. 新建空白 Flow。
3. 配置输入目录、输出目录和工件目录。
4. 拖入节点。
5. 连线。
6. 配置节点 IO。
7. 绑定角色包、技能、连接和工具。
8. 配置阶段输出契约。
9. 配置导出映射。
10. 调试运行。
11. 保存为模板或直接绑定到工程。

高手路径的设计要求：

- 节点库必须支持拖拽。
- 画布必须支持自由摆放。
- Inspector 必须支持完整配置。
- 右键和卡片上的对象级操作必须都可用。

### 5.3 小白路径的真实操作例子
下面是“从一个模糊想法开始”的真实页面操作顺序。

```text
欢迎页
  -> 点击：开始编排
  -> 打开：模板选择页
模板选择页
  -> 点击：软件工厂默认模板
  -> 右侧显示：模板说明、输入目录、输出目录、预期产物
  -> 点击：使用此模板
  -> 打开：编排页
编排页
  -> 默认选中：主流程
  -> 中央画布显示：完整主流程
  -> 右侧 Inspector 显示：当前 Flow 的输入目录、输出目录、工件目录
  -> 用户只修改：输出目录和项目名称
  -> 点击：运行
运行视图
  -> 看到：每个节点状态、生成的工件、阻塞项
  -> 若无阻塞：点击保存为工程
```

这个例子对应的产品要求是：

- 小白不需要先理解角色包、节点 IO、导出映射。
- 小白首次进入时，应先看到“流程会产出什么”，而不是“流程有哪些技术对象”。

### 5.4 高手路径的真实操作例子
下面是“先编排，再绑定工程”的真实页面操作顺序。

```text
欢迎页
  -> 点击：开始编排
  -> 打开：空白编排入口
空白编排入口
  -> 点击：新建空白 Flow
  -> 打开：编排页
编排页
  -> 左侧资产栏：创建主流程、创建角色、创建工件
  -> 中央节点库：拖入开始、角色节点、条件、循环、子流程、结束
  -> 画布中：拖动排列并连线
  -> 选中 Flow：在 Inspector 中配置输入目录和输出目录
  -> 选中角色节点：绑定角色包、输入工件、输出工件、技能覆盖
  -> 选中循环节点：配置退出条件和最大轮次
  -> 选中子流程节点：点击打开子流程，进入子流程编辑
  -> 返回主流程：点击运行
运行视图
  -> 检查：每个节点结果、每个工件结果、当前 blocker
  -> 点击：保存为模板
  -> 后续在新建工程时可直接复用
```

这个例子对应的产品要求是：

- 高手必须能先创建编排，不依赖先有工程。
- 子流程必须能从节点本身直接打开。
- 运行失败时，必须能直接看见是哪一个节点、哪一个工件、哪一个契约失败。

## 6. 编排页的页面结构
编排页是一个专业编辑器页面，不是普通表单页。

### 6.1 页面分区
编排页应固定分为 5 个区。

1. 顶部栏
2. 左侧资产栏
3. 中央节点库与画布
4. 右侧 Inspector
5. 底部运行与调试区

### 6.2 顶部栏
顶部栏负责页面级动作。

至少包含：

- 当前 Flow 名称
- 当前 Flow 状态：草稿 / 已保存 / 运行中 / 有错误
- 保存
- 运行
- 停止
- 切换设计态 / 运行态
- 打开模板中心
- 返回欢迎页或工作台

### 6.3 左侧资产栏
左侧资产栏负责管理编排资产，不负责编辑细节。

至少包含 6 类资产：

- 主流程
- 子流程
- 角色
- 工件
- 连接
- 工具

要求：

- 每类资产都以列表显示。
- 当前选中对象高亮。
- 列表项必须支持对象级操作。
- 常用操作放在卡片上。
- 低频操作放入右键菜单。

### 6.4 节点库
节点库必须以可拖拽的小卡片显示，而不是纯文字列表。

每种节点小卡片应显示：

- 节点图标
- 节点名称
- 一句功能说明

节点库至少包含：

- 开始
- 结束
- 角色节点
- 工具节点
- 工件读取
- 工件写入
- 条件
- 循环
- 并行分叉
- 并行汇合
- 子流程
- 人工确认

### 6.5 画布
画布负责真正的 Flow 编辑。

画布必须支持：

- 节点拖动
- 连线
- 删除线
- 框选
- 缩放
- 平移
- 右键菜单
- 节点位置持久化
- 再打开后恢复上次布局

### 6.6 Inspector
Inspector 是深层配置区，不应该抢占主页面。

它必须能根据选中对象切换内容：

- 选中 Flow：显示目录、工件、契约、导出配置
- 选中 Node：显示 IO、角色、技能、连接、工具、错误策略
- 选中 Role：显示角色包和实例化覆盖项
- 选中 Artifact：显示工件定义和目录规则

### 6.7 运行与调试区
底部运行区用于查看执行结果，不用于编辑结构。

至少包含：

- 节点运行状态
- 错误信息
- 工件生成结果
- 阶段阻塞原因
- 从此继续
- 局部重跑

## 7. 节点类型和具体配置
每类节点都必须有最小配置项。

### 7.1 角色节点
作用：让某个角色处理输入工件并产出新工件。

最小配置：

- 节点名称
- 绑定角色包
- 输入工件列表
- 输出工件列表
- 输入消息列表
- 输出消息列表
- 输出控制信号
- 可选技能覆盖
- 可选连接覆盖
- 可选工具覆盖
- 错误策略

例子：

```text
节点名称：需求梳理
角色包：.project/runtime/roles/sf-role-discover.json
输入工件：01-requirements/01-原始需求.md
输出工件：01-requirements/02-需求澄清.md
输入消息：无
输出消息：.project/runtime/messages/discover_packet.json
输出控制信号：discover_complete=true
技能：read_artifact, write_artifact, browse_web
错误策略：失败重试 2 次，仍失败则阻塞阶段
```

### 7.2 工具节点
作用：调用连接或本地工具执行确定性动作。

最小配置：

- 节点名称
- 工具来源
- 输入参数映射
- 输出工件映射
- 超时策略

例子：

```text
节点名称：导出 PDF
工具来源：local-export/pdf-renderer
输入参数：source=delivery.md
输出工件：delivery.pdf
超时：30s
```

### 7.3 条件节点
作用：按条件决定分支。

最小配置：

- 条件名称
- 条件表达式
- true 分支
- false 分支

例子：

```text
条件名称：需求是否完整
表达式：artifact('clarified-brief').missing_count == 0
true -> 进入功能树生成
false -> 回到信息补全循环
```

### 7.4 循环节点
作用：在满足条件前重复执行一段流程。

最小配置：

- 循环体引用
- 退出条件
- 最大轮次
- 超限策略

例子：

```text
循环体：subflows/review-red-blue
退出条件：review_result.blocker_count == 0
最大轮次：3
超限策略：转人工确认
```

### 7.5 并行分叉和并行汇合
作用：同时执行多个分支，再汇合结果。

最小配置：

- 分叉节点：分支列表
- 汇合节点：等待哪些分支
- 汇合策略：全部成功 / 允许部分失败

例子：

```text
并行分叉：
- 分支 A：生成大纲
- 分支 B：生成角色卡
- 分支 C：生成风险清单

并行汇合：
- 等待 A/B/C 完成
- 若任一失败则阻塞后续阶段
```

### 7.6 子流程节点
作用：调用一个可复用流程片段。

最小配置：

- 子流程引用
- 输入工件映射
- 输出工件映射
- 打开子流程按钮

例子：

```text
子流程：sf-subflow-review
输入工件：01-requirements/04-功能清单.md
输出工件：02-solution/06-审查结论.md
```

要求：

- 子流程节点卡片上必须有“打开子流程”按钮。
- 用户不应先切换资产列表再找子流程。

## 8. 输入目录、输出目录和工件目录的工作方式
每个 Flow 都必须有输入目录和输出目录。

### 8.1 输入目录
输入目录表示流程默认会读哪些目录下的工件。

例子：

```text
input/
  notes/
  attachments/
  references/
```

### 8.2 输出目录
输出目录表示流程默认把正式工件写到哪里。

例子：

```text
01-requirements/
02-solution/
03-openspec/
```

### 8.3 工件目录
工件目录是“正式管理对象”，不是简单文件夹。

例子：

```text
artifacts/
  01-requirements/01-原始需求.md
  01-requirements/02-需求澄清.md
  01-requirements/03-功能树.md
  01-requirements/04-功能清单.md
  02-solution/01-技术方案.md
  02-solution/02-功能实现方案.md
  02-solution/03-流程图.md
  02-solution/04-自动测试方案.md
  02-solution/05-手动验收方案.md
  02-solution/06-审查结论.md
  03-openspec/00-交付摘要.md
```

要求：

- 输入目录用于读。
- 输出目录用于最终正式写。
- 工件目录用于流程内部管理。
- 不允许产品把所有内容都无条件写到固定默认目录。

## 9. 角色包的工作方式
角色包必须以目录形式存在，并由运行时实例化。

当前代码中角色资产有两个落点：

- `.project/platform/roles.json` 与 `.project/platform/roles/<roleId>/` 是工程内角色资产和目录化角色包的权威编辑源，由 `PlatformService` 维护。
- `.project/runtime/roles/*.json` 是 `RuntimeAssetService` 根据平台资产生成的运行时镜像，用于运行资产快照、调试和追踪，不作为角色编辑源。

### 9.1 软件工厂当前角色运行时落盘示例
```text
.project/
  runtime/
    roles/
      sf-role-discover.json
      sf-role-plan.json
      sf-role-blue.json
      sf-role-red.json
      sf-role-judge.json
      sf-role-openspec.json
```

### 9.2 role.json 示例
```json
{
  "id": "sf-role-discover",
  "name": "需求梳理员",
  "description": "负责从一句话需求扩展目标、限制与基础信息",
  "allowedCapabilities": ["read_artifact", "write_artifact", "browse_web"],
  "outputSchema": "markdown-basic",
  "modelPolicy": {
    "mode": "fallback_to_active",
    "preferredProfileIds": [],
    "fallbackToActive": true
  }
}
```

### 9.3 角色实例化方式
实例化过程：

1. 从模板平台资产读取角色定义。
2. 工程创建时把权威角色资产写入 `.project/platform/roles.json` 和 `.project/platform/roles/<roleId>/`。
3. `RuntimeAssetService` 同步运行时镜像到 `.project/runtime/roles/*.json`。
4. 生成角色快照。
5. 叠加 Flow / TaskTemplate / AgentProfile 覆盖项。
6. 叠加节点级连接、工具、技能覆盖项。
7. 生成本次运行的最终角色实例。

要求：

- 角色实例必须可回看。
- 角色实例必须记录实际使用了哪些技能和连接。

## 10. 阶段确认的工作方式
阶段确认不能只是“用户点一下确认按钮”。

阶段确认必须同时满足：

1. 当前阶段必需工件存在。
2. 工件通过校验。
3. 当前运行没有 blocker。
4. 当前阶段至少执行过一次。
5. 若模板要求人工确认，则必须显式确认。

例子：

```text
阶段：方案拆解
必需工件：
- 01-requirements/03-功能树.md
- 01-requirements/04-功能清单.md
- 02-solution/01-技术方案.md

若缺失其中任何一个：
- 阶段确认按钮禁用
- 面板中显示缺失项
```

## 10.1 多 Agent 沟通如何实现
同一个 Flow 中多个 Agent 的沟通，不通过“角色直接决定输出”实现，而通过“节点 IO + 边绑定 + 运行时消息/信号”实现。

### 沟通规则
1. 角色通过 `AGENTS.md` 定义沟通纪律。
2. 节点定义本节点读取哪些工件、读取哪些消息、产出哪些工件、产出哪些消息。
3. 边定义上游输出如何映射给下游输入。
4. 循环节点、条件节点、并行汇合节点读取控制信号，而不是猜测上游意图。

### 红蓝裁判示例
```text
蓝军节点
  输入工件：
  - 01-requirements/04-功能清单.md
  输出工件：
  - 02-solution/review/blue-draft.md
  输出消息：
  - .project/runtime/messages/blue_packet.json

红军节点
  输入工件：
  - 01-requirements/04-功能清单.md
  输入消息：
  - .project/runtime/messages/blue_packet.json
  输出工件：
  - 02-solution/review/red-issues.md
  输出消息：
  - .project/runtime/messages/red_packet.json

裁判节点
  输入工件：
  - 02-solution/review/blue-draft.md
  - 02-solution/review/red-issues.md
  输入消息：
  - .project/runtime/messages/blue_packet.json
  - .project/runtime/messages/red_packet.json
  输出工件：
  - 02-solution/06-审查结论.md
  输出控制信号：
  - review_complete
```

这里的边绑定示意：

```text
蓝军 -> 红军
  blue_packet.json => 红军输入消息

蓝军 -> 裁判
  blue-draft.md => 裁判输入工件
  blue_packet.json => 裁判输入消息

红军 -> 裁判
  red-issues.md => 裁判输入工件
  red_packet.json => 裁判输入消息

裁判 -> 循环节点
  review_complete => 后续主流程进入 OpenSpec 交付
```

这个示例证明：

- 多 Agent 沟通是 Flow 级机制，不是角色自发约定。
- 角色定义的是人格、原则、协作纪律和默认能力。
- 真正的“给谁什么输入、写什么输出、如何进入下一步”由节点和边决定。

## 13. 界面交互中的高频动作和低频动作
为了降低噪音，编排页必须区分高频动作和低频动作。

### 13.1 节点卡片上的高频动作
必须直接显示：

- 打开
- 复制
- 删除
- 运行当前节点
- 若是子流程节点，显示“打开子流程”

### 13.2 右键菜单中的低频动作
可以放入右键：

- 重命名
- 替换角色包
- 替换子流程引用
- 复制节点配置
- 重置尺寸
- 查看运行日志

### 13.3 Inspector 中的深层动作
只放入深层区：

- 错误重试策略
- 并行汇合策略
- 高级输入输出映射
- 调试断点

## 14. 初级程序员实现时的落地顺序
建议按以下顺序开发。

1. 先完成对象模型：Template / Flow / Subflow / Role Package / Artifact / Stage Contract / Export Mapping。
2. 再完成编排页 5 分区页面结构。
3. 再完成节点库拖拽和画布连线。
4. 再完成 Flow 输入目录、输出目录和工件目录配置。
5. 再完成角色包加载与节点绑定。
6. 再完成阶段契约和导出映射。
7. 再完成运行态和调试态。

如果开发顺序颠倒，最容易出现的问题是：

- 角色先做了，但没有工件契约。
- 节点先能显示了，但不知道读写什么。
- 模板先做了，但输出结构仍然被产品写死。

## 16. 反例
以下做法视为错误实现：

- 把输出格式写死在角色中。
- 让阶段确认按钮在没有运行、没有工件、没有校验时也可点击。
- 让子流程只能在侧栏中打开，不能从子流程节点本身打开。
- 让 Flow 没有输入目录和输出目录。
- 让用户无法从欢迎页直接创建编排。
- 让节点拖拽位置被普通编辑操作重置。
