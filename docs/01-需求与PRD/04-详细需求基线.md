# 04 详细需求基线

## 1. 一句话需求
Cyber Editor 是一个以编排层为核心的桌面图文工作台，旨在帮助不知道如何梳理自己想法的用户，把一个模糊想法逐步沉淀为结构化文档、流程和可交付文本产物。

## 1.1 本文档的约束目标
1. 本文档首先用于对齐你和我对产品的理解。
2. 本文档同时必须能让另一套 AI 或另一名程序员，在不依赖外部上下文的情况下，得到高度接近的产品设计。
3. 本文档不要求锁死具体代码实现，但必须尽量锁死：
   - 产品定位
   - 核心对象
   - 主路径
   - 页面层级
   - 功能边界
   - 状态变化
   - 输入输出规则
   - 失败与阻塞条件
4. 对于 `M/S/A` 级功能，本文档的目标是让另一套 AI 在主路径、对象关系和页面设计上做不出另一种产品。
5. 如果某个核心需求仍然能被另一套 AI 解读成两种以上明显不同的产品形态，则该需求仍然不够原子。

## 1.2 可变真相与反硬编码边界
1. 产品不得把模板目录、阶段工件路径、导出路径、Provider 默认值、角色默认行为和业务专属输出结构硬编码进通用代码。
2. 这些可变真相必须由模板包、Flow、角色包、Skill 包、Schema、Provider 注册表、用户输入或运行时状态共同决定。
3. 本项目中“硬编码”的统一定义是：把本应由数据资产或运行时状态决定的可变真相，直接写死在不拥有它的通用代码位置。
4. 更换模板、Provider、角色、Flow 或导出结构后，如果仍必须修改通用代码，视为需求未满足。
5. 产品允许存在内置模板、内置 Skill 和平台协议常量，但它们必须以数据资产或平台契约形式存在，不能散落为业务 `if/else`。

## 2. 使用对象与使用方式需求

### 2.1 目标用户
1. 不知道如何把想法整理清楚的普通用户，需要 AI、模板和现成流程帮助自己完成思路沉淀。
2. 有一定文档整理能力的内容/产品/运营用户，需要可视化编排和模板复用来完成流程梳理、故事创作、攻略整理、视频脚本和拍摄思路设计。
3. 熟悉流程工具或 AI 工作流的高级用户，需要更深层的角色、技能、连接、工具和导出控制。

### 2.2 典型使用方式
1. 从一句话想法开始，在没有工程的情况下先设计 Flow、Subflow、角色和模板草稿。
2. 从模板创建工程，再在工程内补全文档、引用关系、工件和阶段输出。
3. 打开已有工程，对已有文档、流程、会话和导出物继续编辑。
4. 在同一个工程内，一边编辑文档，一边通过 AI 会话和流程面板推进阶段。
5. 在资源中心保存、导入和复用模板、Skill 或角色包，而不是每次都从零开始。

### 2.2.1 典型产物示例
1. 软件方案文档、需求文档、OpenSpec 交付物
2. 流程梳理文档与流程图
3. 故事大纲、人物设定、分章结构
4. 旅游攻略、路线方案、行程说明
5. 视频脚本、拍摄思路、分镜草稿

说明：
- 上述只是示例，不是产品边界。
- 产品不固定用户最终要输出哪一种文档集合。
- 最终输出文档结构、文件夹结构和管理方式，必须由编排流程和模板共同定义，而不是由产品写死。

### 2.2.2 双主路径用户旅程
1. 小白主路径 A：从欢迎页点击 `新建工程`，选择模板后直接进入工程与工作台，默认复用模板预设的编排、工件目录和导出规则。
2. 小白主路径 B：从欢迎页点击 `开始编排`，先使用现成 Flow 或轻度调整流程，再决定是否绑定工程。
3. 高手主路径 A：从无工程编排模式开始，先定义 Flow、Subflow、角色、工件目录和输出契约，再保存为模板或绑定工程。
4. 高手主路径 B：从已有工程进入编排页，重构流程、角色、工件和导出映射。
5. 资源中心必须同时服务上述四条路径，不能只服务“从模板创建工程”。

### 2.3 使用方式必须固化为产品功能
1. “无工程先编排”本身是正式功能，不是临时入口。
2. “从模板创建工程”是正式功能，不是模板浏览页的附带动作。
3. “打开已有工程继续工作”是正式功能，不是欢迎页上的单一按钮。
4. “关闭工程后返回欢迎页或继续编排”是正式功能，不是状态切换细节。
5. “创建编排”和“创建工程”是并列主入口，不存在谁只是附属入口。
6. 小白用户默认直接使用模板和现成流程；高级用户默认可以自定义 Flow、Subflow、角色和工件结构。

## 3. 核心功能需求拆解

### 3.1 D-C1 文本与图文工件能力
目标：产品最终必须围绕文本和图文产物工作，不向代码编辑器或非文本生产工具扩张，也不把产物类型固定死为“软件需求文档”。

#### 3.1.1 真源文档格式
1. 工程内正式文档真源格式必须是 `Markdown (.md)`。
2. 表格类工件允许使用结构化表格文件，至少要支持：
   - `CSV`
   - `TSV`
   - `XLSX` 预览或导出
3. 编排资产、模板元数据、Flow、Subflow、角色、工件、连接、工具配置允许使用结构化数据文件，例如 `JSON`。
4. OpenSpec 导出结果是一个文件夹结构，不是单个文件。
5. 产品必须允许不同模板定义不同的工件目录和文件组织方式，不能由产品统一写死单一文档结构。

#### 3.1.2 导入格式
1. 文本文档导入范围至少包含：
   - `Markdown (.md)`
   - `Text (.txt)`
2. 图片资源导入范围至少包含：
   - `PNG`
   - `JPG/JPEG`
   - `WEBP`
   - `GIF`
   - `SVG`
3. 不要求当前阶段支持：
   - 代码文件作为编辑主对象
   - 音频、视频作为主产物

#### 3.1.3 图文块与嵌入式内容
1. 文档区必须支持文本块。
2. 文档区必须支持 `Mermaid` 流程图。
3. 文档区必须支持思维导图块。
4. 文档区必须支持框图或普通结构框图块。
5. 文档区必须支持图片块。
6. 文档区必须支持对图、表、工件的超链接引用。
7. 文档区必须支持把图、表、工件以内嵌或卡片预览的方式嵌入文档。
8. 文档区必须支持引用关系展示和引用对比。

#### 3.1.4 导出格式
1. 通用交付至少支持：
   - `Markdown`
   - `TXT`
   - `PDF`
2. 规范交付至少支持：
   - `OpenSpec 文件夹`
3. 导出时必须明确：
   - 导出读取哪些工件
   - 导出格式如何映射
   - 哪些中间输出不进入最终交付
4. 不同模板可以定义不同的默认导出组合，不要求所有模板都导出 OpenSpec。
5. 表格类输出在需要时必须可导出为结构化表格文件，而不是强行转成 Markdown 文本。

#### 3.1.5 输出结构定义原则
1. 产品不能预设单一固定的文档树、章节树或交付树作为全平台标准结果。
2. 模板只提供默认结构，不是强制结构。
3. 编排必须允许定义：
   - 输入文档目录
   - 输出文档目录
   - 工件目录
   - 工件命名规则
   - 阶段输出要求
   - 节点输入输出关系
   - 导出目标与文件夹映射
4. 当同一个产品场景下存在多种可交付结构时，平台必须允许多个模板或多个流程版本并存。

### 3.2 D-C2 编排层核心工作方式
目标：编排页是产品核心，不是附属页面；但从用户入口看，“创建编排”和“创建工程”必须是并列主路径。

#### 3.2.0 编排与工程的关系
1. 编排负责定义：
   - 输出工件有哪些
   - 输出文件如何组织
   - 阶段如何推进
   - 角色如何协作
   - 导出如何映射
2. 工程负责承载：
   - 具体文档内容
   - 文件与资源
   - 会话和运行记录
   - 工件实例
3. 小白用户通常先选模板或现成流程，再进入工程。
4. 高级用户通常先定义或调整编排，再决定是否绑定工程、保存为模板或直接复用。
5. 因此：
   - 欢迎页必须同时支持“开始编排”和“新建工程”
   - 资源中心的模板视图必须同时服务“编排复用”和“工程创建”
   - 编排页必须允许在没有工程时先形成草稿资产并持续保存

#### 3.2.1 编排资产范围
用户必须能管理以下资产：
1. `Flow`
2. `Subflow`
3. `Role`
4. `Artifact`
5. `Connector`
6. `Tool`
7. `Template`
8. `Stage Contract`
9. `Export Mapping`
10. `Runtime Session`

要求：
- `Artifact`、`Stage Contract`、`Export Mapping` 必须是编排页中的一等对象，不能被藏成角色或节点的附属字段。
- 用户在编排页中必须能直接看见“这个 Flow 最终会产出什么”，而不是只能看见节点和连线。

#### 3.2.2 画布基础操作
1. 节点必须可以从节点库拖拽进入画布。
2. 节点必须可以拖动并持久保存位置。
3. 节点之间必须可连线，且流向可读。
4. 节点必须有对象级常用操作按钮。
5. 节点和画布都必须支持右键菜单。
6. 左右面板必须支持缩放、折叠和记忆。
7. 紧凑宽度下布局不能错位、遮挡、挤爆。
8. 编排页必须支持把常用节点以小卡片拖入画布，而不是只能通过文本列表创建。
9. 画布必须支持缩放、平移、Fit View。
10. 画布必须支持框选、多选、撤销、重做。
11. 画布必须支持基础对齐和分布。
12. 画布必须支持最小地图或总览视图。
13. 画布必须支持注释、说明或便签层，便于非技术用户理解流程。

#### 3.2.3 流程控制语义
编排页必须明确支持这些控制语义：
1. 条件分支
2. 循环
3. 并行分叉
4. 并行汇合
5. 并行分支通信策略
6. 子流程
7. 设计态与运行态切换
8. 节点级调试与从此继续
9. 历史、快照和恢复

并且每类控制节点都必须定义：
1. 输入条件
2. 执行策略
3. 成功条件
4. 超时条件
5. 失败策略
6. 输出合并方式
7. UI 可编辑字段

#### 3.2.4 角色工作方式
1. 一个 Flow 内必须允许多个角色。
2. 每个角色至少要定义：
   - 目标
   - 设定
   - 角色类型
   - 系统提示/行为边界
   - 允许技能
   - 权限边界
   - 模型策略
   - 记忆/上下文策略
3. 输出格式不属于角色本身，而属于：
   - 节点输入输出契约
   - 阶段输出契约
   - 导出映射
4. 每一种角色定义都必须有自己的角色目录，目录内至少要保存：
   - `role.json`
   - `IDENTITY.md`
   - `SOUL.md`
   - `AGENTS.md`
   - `USER.md`
   - `Skills/`
   - `MEMORY/MEMORY.md`
5. `IDENTITY.md` 用于定义名称、角色定位、专注领域和身份识别信息。
6. `SOUL.md` 用于定义人格、价值观、说话风格和做事原则。
7. `AGENTS.md` 用于定义该角色在多 Agent 协作中的处理流程、输入规则、输出纪律、升级条件和冲突处理方式。
8. `USER.md` 用于定义该角色默认服务对象画像、偏好、禁忌和适配策略。
9. 实例化角色时，系统必须先加载角色目录，再在当前 Flow/节点上下文中附加技能、连接和模型覆盖策略。
10. 节点必须可以绑定角色、连接和工具。
11. 角色定义采用“角色包 + 协作制度 + 技能目录 + 记忆目录”分离结构，避免把 prompt、技能、权限和输出规则揉成一个不可复用的大表单。
12. 同一个 Flow 内多个角色之间的相互沟通，必须由节点 IO、边绑定和运行时消息/信号机制实现，而不是由角色直接定义最终文件格式。

#### 3.2.5 工件与输出契约
1. 模板必须定义工件目录。
2. 每个 Flow 必须定义输入文档目录和输出文档目录。
3. 阶段必须定义本阶段应输出哪些工件。
4. 节点必须定义输入工件和输出工件。
5. 节点还必须定义输入消息、输出消息和输出控制信号。
6. 导出必须定义工件到目标格式的映射关系。
7. 多 Agent 协作中的中间沟通结果，允许以临时消息方式存在，不必全部成为最终工件。
8. 条件、循环、并行汇合和人工确认，必须依赖显式控制信号，而不是隐式猜测上游结果。
9. 表格、图形、文档三类工件都必须能进入同一套工件契约与导出映射。
10. 运行时必须能显示工件完成状态。
11. 工件结构和文件管理规则必须由编排和模板定义，不能由产品预设一个固定结果结构强加给所有场景。
12. 编排页必须能让用户直接看出“这个流程最终会产出什么”，而不是只看见节点和连线。

#### 3.2.6 设计态与运行态分离
1. 编排页必须强制分为 `设计态` 和 `运行态`。
2. 设计态负责：
   - 节点
   - 连线
   - 角色
   - 工件
   - 输出契约
   - 导出映射
3. 运行态负责：
   - 节点状态
   - 工件状态
   - 消息/信号状态
   - blocker
   - 从此继续
   - 局部重跑
4. 设计态与运行态的工具栏、Inspector 和底部面板必须区分，不允许所有内容同时铺开。

#### 3.2.7 阶段确认与硬边界
1. 阶段确认不能只是一个普通按钮。
2. 阶段确认的合法条件至少包括：
   - 输入完整
   - 本阶段必需工件完成
   - 阻塞问题为 0
   - 最近关键运行成功
3. 若模板要求人工确认，则必须额外显式确认。
4. Guard 不通过时：
   - 阶段确认按钮必须禁用
   - 流程面板必须显示不满足项列表
   - 系统必须给出阻塞原因，而不是模糊提示

#### 3.2.8 无工程编排模式闭环
1. 无工程编排模式必须支持：
   - 新建草稿 Flow
   - 保存本地草稿
   - 恢复草稿
   - 导出 Flow 包
   - 保存为模板
   - 后续绑定工程
2. 没有这些能力，无工程编排模式不能算正式模式。

#### 3.2.9 编排页的具体操作效果要求
以下要求用于约束编排页不只“能显示”，而是“能真正工作”。

1. 当用户从节点库拖入一个角色节点时：
   - 画布中必须立即出现该节点
   - 节点必须有默认名称、默认图标和未配置状态
   - 右侧 Inspector 必须自动切换到该节点配置
2. 当用户拖动节点位置时：
   - 节点位置必须立即更新
   - 该位置必须写入当前 Flow 草稿
   - 切换选中对象、切换资产类型、折叠面板、重新打开 Flow 后，位置必须保持不变
3. 当用户创建一条边时：
   - 系统必须显示这条边的流向
   - 边必须可点击并编辑
   - 若源节点输出和目标节点输入不兼容，边必须显示错误态
4. 当用户配置条件节点时：
   - 必须能编辑条件表达式
   - 必须能看见 true/false 两个出口
   - 若任何出口未连接，系统必须标记为流程不完整
5. 当用户配置循环节点时：
   - 必须能编辑退出条件、最大轮次、超限策略
   - 必须能看见循环体引用或循环范围
   - 若退出条件为空，运行时必须阻止执行
6. 当用户配置并行分叉与汇合时：
   - 必须能明确看见有哪些分支
   - 必须能配置汇合等待策略
   - 必须能配置分支之间通过工件、消息和信号沟通
7. 当用户点击子流程节点上的“打开子流程”：
   - 必须直接打开该子流程编辑视图
   - 返回主流程时必须保留原视口、选中态和滚动位置
8. 当用户切换设计态与运行态时：
   - 设计态中的结构编辑控件必须隐藏或禁用运行态专用信息
   - 运行态必须突出显示节点状态、工件状态、blocker、重跑入口
9. 当用户点击“运行当前节点”：
   - 运行结果必须进入运行记录
   - 该节点相关的工件、消息和信号结果必须可见
10. 当用户点击“从此继续”或“局部重跑”：
   - 系统必须显示将从哪个节点继续、会复用哪些已完成结果、会重置哪些结果
11. 当用户未配置必需项时：
   - 系统必须在首层给出缺失项，不得把关键错误藏进深层面板
12. 编排页默认必须优先满足小白用户的“看懂流程会产出什么”，而不是优先展示全部高级配置。

### 3.3 D-C3 四层 AI 架构与模型工作方式
目标：AI 行为必须由架构和编排共同约束，而不是靠硬编码提示词临时拼接。

#### 3.3.1 四层架构边界
1. 智能层：只负责推理、生成、结构化输出和模型调用。
2. 编排层：负责流程、角色、阶段、循环、并行、子流程和运行控制。
3. 连接层：负责连接、协议、发现、授权、传输和能力注册。
4. 能力层：负责工具、技能、脚本工具、导出器和领域能力。

#### 3.3.2 模型接入范围
当前阶段至少支持：
1. `DeepSeek`
2. `OpenAI-compatible`
3. `Ollama`

#### 3.3.3 模型选择原则
1. 模型选择必须由角色或节点策略驱动。
2. 不能要求用户先手动切全局模型，才能让某个角色工作。
3. 角色实际命中哪个模型，必须对用户可见。
4. 本地模型必须支持真实连通性测试和真实生成验证。

#### 3.3.4 AI 过程显性化
用户必须能看到：
1. 当前阶段
2. 当前 guard 状态
3. 当前运行记录
4. 红蓝裁判过程
5. 审查问题及处理状态
6. 当前会话上下文
7. 命中模型

### 3.4 D-C4 模板体系
目标：模板是平台正式资产，不是固定写死的几张入口卡片。

#### 3.4.1 默认模板
1. 默认至少提供 `软件工厂` 模板。
2. 允许后续存在 `小说创作`、`视频脚本`、`旅游攻略` 等模板。
3. `软件工厂` 只是默认模板之一，不代表产品只服务软件场景。

#### 3.4.2 模板生命周期
用户必须能：
1. 查看模板
2. 搜索和筛选模板
3. 从模板创建工程
4. 保存当前工程为模板
5. 从目录导入模板
6. 从网络下载模板
7. 查看最近使用过的模板
8. 查看模板来源：内置 / 本地 / 远程
9. 查看模板版本和兼容性
10. 查看模板信任状态：官方 / 用户导入 / 未验证
11. 更新模板
12. 删除模板
13. 从模板直接进入编排继续调整，而不是只能创建工程

#### 3.4.3 模板与编排的关系
1. 模板不只是文档脚手架，还必须包含：
   - 默认工件目录
   - 默认流程
   - 默认角色
   - 默认导出映射
2. 模板中心必须和编排页互通。

#### 3.4.4 模板中心的具体操作效果要求
1. 用户进入模板中心时，必须立即能分辨：
   - 内置模板
   - 最近使用模板
   - 本地导入模板
   - 远程可下载模板
2. 用户点击任一模板时，右侧详情区至少要显示：
   - 模板说明
   - 适用场景
   - 默认 Flow
   - 默认工件目录
   - 输入目录与输出目录
   - 导出映射
   - 来源、版本、兼容性、信任状态
3. 用户在模板中心必须至少能执行 5 个一级动作：
   - 使用模板创建工程
   - 使用模板开始编排
   - 导入模板
   - 下载模板
   - 查看最近模板
4. 用户安装或导入模板后：
   - 模板必须立即进入模板列表
   - 必须显示来源和状态
   - 若模板损坏或版本不兼容，必须阻止使用并说明原因
5. 用户保存当前工程或当前编排为模板后：
   - 模板必须写入模板注册表
   - 必须能在模板中心和欢迎页最近模板中立即看见
6. 模板中心不得退化为只有“固定卡片 + 创建工程”这一种交互。

### 3.5 D-C5 知识关系与可审查性
目标：文档之间不是孤立文件，而是有关系的知识网络。

#### 3.5.1 引用能力
1. 文档必须支持正向引用查看。
2. 文档必须支持反向引用查看。
3. 必须支持两篇笔记之间的引用对比。

#### 3.5.2 可审查性
1. 阶段推进前必须能看到阻塞项。
2. 审查结果必须可见、可采纳、可忽略、可待处理。
3. 运行失败和重试必须有记录。

### 3.6 D-C6 大工程文档知识底座与上下文管理
目标：当工程文档规模很大时，平台必须提供一套本地、可追溯、可增量刷新的知识底座，避免模型每次都全量读取全部文档。

#### 3.6.1 合理性判断
1. 该需求合理，而且应作为正式产品能力，而不是后期优化。
2. 仅依赖“把所有文档塞进上下文”无法支撑大工程。
3. 单纯的向量检索也不够，因为文档、工件、流程、角色、模板之间存在强关系。
4. 更合适的方向是“本地混合检索 + 文档图谱 + 上下文打包”。

#### 3.6.2 产品效果要求
1. 当工程文档很多时，用户必须仍然能快速定位相关文档、章节、工件和流程。
2. AI 在生成阶段草稿、运行角色节点、执行审查时，必须能自动选择相关上下文，而不是盲目读取整个工程。
3. 用户必须能看到：
   - 这次运行用了哪些文档
   - 为什么选这些文档
   - 哪些是关键词命中
   - 哪些是语义命中
   - 哪些是引用扩展带出来的
4. 用户必须能手动固定、排除或替换上下文集合。

#### 3.6.3 数据对象范围
知识底座至少要纳入以下对象：
1. 文档
2. 文档章节或块
3. 工件
4. Flow
5. Subflow
6. Role
7. Template
8. 导出映射
9. 运行记录

#### 3.6.4 关系类型
知识底座至少要支持这些关系：
1. `references`：文档引用文档
2. `embeds`：文档嵌入工件
3. `belongs_to`：对象归属某个 Flow/模板/工程
4. `produces`：节点或流程产出工件
5. `consumes`：节点或流程读取工件
6. `generated_from`：某个结果由哪些来源生成
7. `variant_of`：模板或 Flow 的变体关系
8. `used_by`：技能、连接、工具被哪些角色或节点使用

#### 3.6.5 检索方式
检索必须采用混合方式，至少包含：
1. 关键词检索
2. 语义检索
3. 引用图谱扩展
4. 结果重排
5. 基于任务的上下文打包

#### 3.6.6 运行效果要求
1. 当用户触发某个阶段、节点或导出动作时，系统必须生成一个“上下文包”。
2. 上下文包至少包含：
   - 主命中文档
   - 扩展关联文档
   - 关联工件
   - 关联流程片段
   - 来源说明
   - token 预算说明
3. 上下文包必须可缓存、可复用、可重新生成。
4. 若索引过旧或缺失，系统必须提示并支持增量刷新。

#### 3.6.7 技术实现路径
1. 默认采用本地索引，不要求把工程文档上传到远端。
2. 索引层建议采用“GitNexus 类思路”，即：
   - 先扫描结构
   - 再解析对象
   - 再建立关系图
   - 再建立混合搜索索引
3. 但本产品不直接照搬 GitNexus 的代码仓语义，而要改成面向：
   - 文档
   - 工件
   - Flow
   - Role
   - Template
4. 索引必须持久化到工程内部隐藏目录或应用工作区，不得只存在内存中。
5. 索引刷新至少支持：
   - 初次全量构建
   - 文件变更后增量刷新
   - 手动重建

#### 3.6.8 用户操作与预期结果
1. 用户在知识视图中搜索“红蓝审查”，系统应同时返回：
   - 子流程定义
   - 相关角色包
   - 相关审查文档
   - 相关运行记录
2. 用户点击“为当前阶段推荐上下文”时，系统应生成可审查的上下文包。
3. 用户排除某个文档后，后续本轮运行不得继续偷偷使用该文档。
4. 用户查看某次 AI 结果时，必须能追溯它主要引用了哪些文档和工件。

## 5. 需求与功能树/功能清单的映射规则
1. 每一个需求项，后续都必须映射到 `05-功能树.md` 中至少一个原子功能。
2. 每一个原子功能，必须能回溯到本需求文档中的某一条需求。
3. 如果需求存在，但功能树/功能清单中还没有对应项，必须在本需求文档中先标记为“待映射”，不能假装已经覆盖。
4. 功能树负责“层级和从属关系”，功能清单负责“原子功能状态”，本需求文档负责“为什么必须有这个功能”。

## 5.1 原子化要求
1. 需求写到原子，不是把一句抽象口号拆成几个同样抽象的小标题。
2. 一个需求只有同时回答清楚下列问题，才能视为足够原子：
   - 谁会用
   - 从哪里进入
   - 会做什么动作
   - 系统应如何反馈
   - 完成后留下什么状态
   - 失败时如何阻断或恢复
   - 它与哪些对象、页面、流程节点直接相关
3. 对于 `M/S/A` 级需求，必须进一步写清：
   - 不允许出现的错误实现
   - 不允许模糊处理的边界
   - 另一套 AI 最容易做歪的地方
4. 需求层不直接定义组件代码，但必须定义用户视角下的具体效果，直到不同实现者只能在代码方式和少量交互细节上有差异。
