# 总评

## 结论
当前这套合并后的文档，比之前的分散修补稿清晰得多，但距离“可以冻结方案并高质量开发”还有明显差距。最大的问题不是视觉风格，而是产品核心闭环没有在文档层真正收口：

1. 产品宣称“以编排层为核心”，但双主入口、无工程模式、阶段约束、工件契约、并行语义都没有闭合。
2. UI 文档已经按页面拆开，但页面之间的导航语义、对象层级、默认模式与高级模式仍然带有明显占位感。
3. 文档已经明确产品不是只服务软件场景，但功能和页面设计里仍然存在把输出结构默认为“某类固定文档树”的风险。
4. 原子功能文档数量够了，信息密度不够。大量条目还是模板化描述，尚未达到“一个不了解背景的初级程序员可以 1:1 复刻”的标准。

## 严重级别最高的问题

### P0-1 双主路径没有被文档明确成立
- 受影响文档：
  - [01-需求](../01-需求.md)
  - [欢迎页](../04-UI设计/01-欢迎页.md)
  - [新建工程与模板中心](../04-UI设计/02-新建工程与模板中心.md)
  - [无工程编排模式](../04-UI设计/10-无工程编排模式.md)
  - [F-005 欢迎页无工程直接进入编排页](../05-功能具体实现方案/01-平台入口与模板/F-005-欢迎页无工程直接进入编排页.md)
  - [F-060 无工程状态进入编排页](../05-功能具体实现方案/05-编排与流程资产/F-060-无工程状态进入编排页.md)
- 问题：
  - 文档口径说编排是产品核心，但“创建编排”和“创建工程”没有被设计成并列主路径。
  - 这会让首屏入口含义模糊：既不像真正的编排驱动平台，也不像工程驱动平台。
- 原因：
  - 核心体验和传统工程入口并存，但没有被定义为“双主入口”。
  - 无工程编排模式只有页面壳，没有独立草稿生命周期。
- 解决方案：
  - 欢迎页必须同时提供两个一级 CTA：`开始编排` 和 `新建工程`。
  - `打开已有工程` 作为第三个主动作存在。
  - 无工程编排必须支持：创建草稿 Flow、保存草稿、另存为模板、后续绑定工程。
  - 新建工程与模板中心和无工程编排模式之间的关系，必须在文档中被明确成两条并列路径，而不是主次关系。

### P0-1A 输出结构仍然有被产品默认绑死的风险
- 受影响文档：
  - [01-需求](../01-需求.md)
  - [02-功能树](../02-功能树.md)
  - [03-功能清单](../03-功能清单.md)
  - [编排页](../04-UI设计/07-编排页.md)
- 问题：
  - 虽然需求已经写明“输出结构由模板和编排定义”，但功能树、清单和页面描述还没有彻底形成同一套表达。
  - 在后续开发中，仍有很大概率被误实现成产品预设一套固定结果结构。
- 原因：
  - 工件目录、阶段输出、节点 IO、导出映射虽然列了功能，但还没有在用户主路径中被当成首要对象。
- 解决方案：
  - 在编排主路径里，把“工件目录 / 输出契约 / 导出映射”明确成与角色、流程同等级的一等对象。
  - 在模板中心和无工程编排模式里，也要让用户看见“这个模板/流程最终定义了什么输出结构”。 

### P0-2 阶段系统没有硬边界
- 受影响文档：
  - [流程面板](../04-UI设计/06-流程面板.md)
  - [F-048 阶段 guard 检查结果展示](../05-功能具体实现方案/04-AI会话与阶段控制/F-048-阶段guard检查结果展示.md)
  - [F-049 只有满足 guard 才允许阶段确认](../05-功能具体实现方案/04-AI会话与阶段控制/F-049-只有满足guard才允许阶段确认.md)
  - [F-088 阶段输出契约配置](../05-功能具体实现方案/06-模板工件与导出/F-088-阶段输出契约配置.md)
  - [F-091 运行输出落到工件并显示完成状态](../05-功能具体实现方案/06-模板工件与导出/F-091-运行输出落到工件并显示完成状态.md)
- 问题：
  - 当前阶段确认在文档上仍然没有形成“输入充分 + 工件完整 + 阻塞问题已清”的硬门槛。
  - 这会让流程面板沦为展示区，而不是流程控制器。
- 原因：
  - Guard、输出契约、工件状态、审查问题四套机制分别列了功能，但没有被定义成一个统一的阶段机。
- 解决方案：
  - 明确阶段确认计算公式：
    - `guard = 输入完整 && 本阶段必需工件完成 && 阻塞 issue 为 0 && 最近关键运行成功`
  - 流程面板顶部固定展示“不满足项列表”。
  - Guard 不通过时，确认按钮必须不可点击，且显示阻塞原因而不是提示语。

### P0-3 编排页还不是一个可用编辑器
- 受影响文档：
  - [编排页](../04-UI设计/07-编排页.md)
  - [编排与流程资产 README](../05-功能具体实现方案/05-编排与流程资产/README.md)
  - [F-064 拖拽节点进入画布](../05-功能具体实现方案/05-编排与流程资产/F-064-拖拽节点进入画布.md)
  - [F-069 并行分叉与并行汇合配置](../05-功能具体实现方案/05-编排与流程资产/F-069-并行分叉与并行汇合配置.md)
  - [F-084 节点级调试与从此继续](../05-功能具体实现方案/05-编排与流程资产/F-084-节点级调试与从此继续.md)
  - [F-086 Flow 历史、快照与恢复](../05-功能具体实现方案/05-编排与流程资产/F-086-Flow历史、快照与恢复.md)
- 问题：
  - 现有文档承认：拖拽、并行、调试、历史、无工程模式、设计/运行态分离都没有收口。
  - 在这个前提下，不能再把编排页定义成产品主核心页。
- 原因：
  - 现在的功能树列出了对象，却没有形成“成熟编辑器的最小能力包”。
- 解决方案：
  - 先冻结“可用编排器最小闭环”：
    - 节点库拖拽入画布
    - 画布移动/缩放/框选/多选/对齐
    - 连线建立/删除/校验提示
    - 条件/循环/并行/子流程的最小运行语义
    - 节点卡片常用动作
    - Inspector 详细编辑
    - 保存/恢复/版本
    - 调试与局部重跑

## 这轮评审的总体判断
- 产品方向是对的：编排驱动的文本工件平台成立。
- 当前文档基线仍然偏“中期设计稿”，不是“可以直接交给团队并稳定实现的施工图”。
- 后续整改优先级应是：
  1. 首屏入口与信息架构回正
  2. 编排页最小可用编辑器闭环
  3. 阶段控制与工件契约硬闭环
  4. 原子功能文档去模板化，改成真正的实现手册
