# 方案文档可实施性评审

## 结论
当前文档体系已经做到“功能全覆盖、有链接、有状态”，但还没有做到“初级程序员按文档即可高保真复刻”。最大问题是：原子功能文档数量够，实施密度不够。

## 发现 1：大量原子功能文档仍是通用模板，不是具体设计
- 严重级别：致命
- 证据文档：
  - [F-009 从模板创建工程](../05-功能具体实现方案/01-平台入口与模板/F-009-从模板创建工程.md)
  - [F-049 只有满足 guard 才允许阶段确认](../05-功能具体实现方案/04-AI会话与阶段控制/F-049-只有满足guard才允许阶段确认.md)
  - [F-064 拖拽节点进入画布](../05-功能具体实现方案/05-编排与流程资产/F-064-拖拽节点进入画布.md)
  - [F-069 并行分叉与并行汇合配置](../05-功能具体实现方案/05-编排与流程资产/F-069-并行分叉与并行汇合配置.md)
  - [F-092 导出 md/txt/pdf](../05-功能具体实现方案/06-模板工件与导出/F-092-导出md-txt-pdf.md)
- 不合理点：
  - 这些文档的“具体实现方案”基本是统一模板句式：
    - 页面提供入口
    - 服务层承担核心实现
    - 数据要持久化
    - 失败要保留上下文
  - 这不构成实现设计。
- 为什么不合理：
  - 初级程序员拿到这类文档后，仍然不知道：
    - 具体改哪个组件
    - 用什么状态结构
    - 需要什么 IPC
    - 输入输出 payload 长什么样
    - 校验失败如何反馈
- 解决方案：
  - 每个原子文档必须改为固定的 12 段：
    1. 用户目标
    2. 页面入口与对象入口
    3. 组件职责
    4. 状态结构
    5. 主进程服务
    6. IPC/命令接口
    7. 持久化结构
    8. 校验规则
    9. 错误处理
    10. 观测与日志
    11. 自动测试
    12. 用户模拟测试

## 发现 2：页面文档和功能文档的调用关系还不够工程化
- 严重级别：高
- 受影响文档：
  - [04-UI设计](../04-UI设计)
  - [05-功能具体实现方案](../05-功能具体实现方案)
- 不合理点：
  - 页面文档能链接到功能文档，但功能文档没有反向说明：
    - 渲染组件
    - 触发命令
    - 对应 service
    - 对应 store
    - 对应测试文件
- 为什么不合理：
  - 链接存在，不代表工程可追踪。
- 解决方案：
  - 给每个原子功能文档增加“实现定位”区块：
    - renderer 组件
    - main service
    - shared types
    - store/key
    - 自动测试文件

## 发现 3：完成状态缺少证据字段
- 严重级别：高
- 受影响文档：
  - [03-功能清单](../03-功能清单.md)
  - [05-功能具体实现方案](../05-功能具体实现方案)
- 不合理点：
  - 当前只有 `已完成 / 部分完成 / 未完成`，但没有说明“为什么是这个状态”。
- 为什么不合理：
  - 这会让状态判断依赖作者记忆，而不是证据。
- 解决方案：
  - 每个原子功能文档补“完成证据”：
    - 主链路代码位置
    - 自动测试名
    - 最近一次人工验证日期
    - 已知缺口

## 发现 4：测试章节仍然过于泛化
- 严重级别：高
- 证据文档：
  - 任意抽查的原子功能文档都采用相同测试模板
- 不合理点：
  - “单元/集成/回归”这种分类没错，但没有写出动作级预期。
- 为什么不合理：
  - 对复杂交互尤其是编排页，测试必须写成：
    - 用户操作
    - 预期画布变化
    - 预期数据落盘
    - 预期状态提示
- 解决方案：
  - 对 S/M 级功能必须补充动作级测试表。
  - 特别是：
    - 编排页
    - 模板中心
    - 流程面板
    - 无工程编排模式

## 发现 5：文档没有明确“未实现但已设计”的边界处理方式
- 严重级别：中
- 受影响文档：
  - [03-功能清单](../03-功能清单.md)
  - [05-功能具体实现方案](../05-功能具体实现方案)
- 不合理点：
  - 虽然状态已经区分，但未实现功能的文档仍然和已实现功能长得几乎一样。
- 为什么不合理：
  - 读文档的人很容易误以为：既然都有实现方案，那应该已经差不多能做。
- 解决方案：
  - 未完成功能统一增加醒目标记：
    - `当前为设计稿，不可按已落地能力对外承诺`
  - 部分完成功能补“已实现范围 / 未实现范围”。

## 发现 6：针对编排页，文档还缺少“行业习惯映射”
- 严重级别：中
- 受影响文档：
  - [编排页](../04-UI设计/07-编排页.md)
  - [编排与流程资产 README](../05-功能具体实现方案/05-编排与流程资产/README.md)
- 不合理点：
  - 文档没有明确哪些交互沿用成熟编排器习惯。
- 为什么不合理：
  - 用户会天然把本产品和 Comfy、n8n、Dify、Langflow 这类工具比较。
  - 如果不明确对齐哪些习惯，工程师实现时会自由发挥。
- 解决方案：
  - 在编排页总文档里加“行业交互映射”：
    - 画布拖拽
    - 节点卡片操作
    - Inspector 编辑
    - 右键语义
    - 运行调试入口

## 最终建议
文档系统下一步不要继续横向加文档数量，而是纵向加密度。最优动作不是“再补一批优化记录”，而是：

1. 把 S/M 级原子功能文档全部重写到实现级。
2. 给每个原子功能补完成证据。
3. 给每个页面补导航语义和动作矩阵。
4. 给编排页单独补行业交互映射和运行语义表。
