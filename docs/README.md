## 当前整理原则

1. 根目录只保留当前 canonical 目录，不再保留旧版 `04-UI设计/`、`05-功能具体实现方案/`、`评审记录/` 一类平行入口。
2. 需要保留的历史细节统一迁入 `06-详细设计库/`，但不把它当成第二套裁决源。
3. 代码可对照的现行结构以 `03-架构实现/` 为主，总细节和原子级约束再下钻到 `06-详细设计库/`。
4. 测试验收口径只看 `04-测试验收/`，不再沿用旧编号文件名或旧路径引用。

## 完成定义

任何能力只有同时满足以下条件，才能标记为已完成：

1. 文档一致：PRD、产品设计、架构、详细设计、测试口径不冲突。
2. 代码有 owner：页面、状态、IPC、服务、持久化、恢复、治理责任清楚。
3. 用户能走通：用户能从真实入口完成任务并看到结果。
4. 测试能证明：覆盖主旅程、关键失败路径和恢复路径。
5. 打包态可验证：用户可见能力最终用 `out/package/` 下的打包应用证明。

接口可调用、页面能打开、状态标签写了“已完成”，都不等于成熟完成。

## 细节保全原则

简洁 PRD 负责裁决方向，不能替代详细实现材料。详细设计、原子功能、UI 页面说明、代码唯一性文档和开发设计统一保存在 `06-详细设计库/`。后续合并文档时，必须先迁移细节、标明冲突裁决，再删除重复表述；不得直接删除尚未吸收的实现细节。
