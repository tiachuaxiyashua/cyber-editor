## 目录职责

| 目录 | 作用 | 不承担 |
|---|---|---|
| `00-总览与导航/` | 一句话需求、核心需求、功能层级、PRD、架构、实现和代码对照的阅读导航 | 取代各层权威文档 |
| `01-需求与PRD/` | 产品定位、用户旅程、范围优先级、详细需求基线、功能树、功能清单 | 代码实现细节和测试结果 |
| `02-产品设计/` | 页面结构、主次动作、编排工作台、关键交互裁决 | 服务 owner 和持久化协议 |
| `03-架构实现/` | 当前代码分层、owner、运行时、数据契约、安全和代码映射 | 抽象愿景或与代码不对应的架构图 |
| `04-测试验收/` | 验收门禁、旅程测试、自动化/手工验证、证据矩阵、需求实现追踪、测试编目 | 未执行的证明或第二套功能状态 |
| `05-项目规则/` | AI 协作规则、变更流程、完成定义、文档治理和交付路线 | 产品需求裁决 |
| `06-详细设计库/` | UI 详细设计、原子功能实现方案、代码契约、模块开发设计、参考分析 | 平行 PRD 或平行测试真相 |
| `99-临时报告/` | 短期审计、梳理和迁移报告，记录缺陷与处理结果 | 长期真相源或替代正式目录 |

## 使用规则

1. 需求基线、功能树和功能清单只放在 `01-需求与PRD/`。
2. 测试口径、证据矩阵和需求到实现追踪只放在 `04-测试验收/`。
3. 实现级细节统一放在 `06-详细设计库/`，但不得覆盖 `01-需求与PRD/` 的产品裁决。
4. 机器生成的测试索引产物只放在 `04-测试验收/generated/`，它们服务测试门禁，不是第二套文档真相。
5. 合并旧内容时必须先迁移仍有效的信息，再删除重复或冲突文件；不得用“简化文档”删掉尚未吸收的实现细节。
6. 临时报告必须放在 `99-临时报告/`，并明确哪些结论已经回写到正式文档、哪些仍是待办缺口。

## 完成定义

任何能力只有同时满足以下条件，才允许标记为成熟完成：

1. 文档一致：PRD、产品设计、架构、详细设计和测试口径不冲突。
2. 代码有 owner：页面、状态、IPC、服务、持久化、恢复和治理边界清楚。
3. 用户能走通：用户能从真实入口完成任务并看到结果。
4. 测试能证明：覆盖主旅程、关键失败路径和恢复路径。
5. 打包态可验证：用户可见能力最终能用 `out/package/` 下的打包应用证明。

接口可调用、页面能打开、状态标签写了“已完成”，都不等于成熟完成。
