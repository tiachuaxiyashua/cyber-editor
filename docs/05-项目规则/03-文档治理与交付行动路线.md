# 03 文档治理与交付行动路线

## 1. 目标
本路线用于约束 Cyber Editor 后续所有需求整理、方案编写、change 管理、开发、自测、评审和文档归档方式。后续沟通默认以本路线和当前合并后的基线文档为准。

## 1.1 产品定位固定口径
1. Cyber Editor 是通用文本/图文思路梳理与编排平台，不是只做软件需求梳理的工具。
2. `软件工厂` 只是默认模板之一，不是产品唯一场景。
3. 用户最终输出什么文档集合，不由产品写死，而由模板和编排流程共同定义。
4. 从入口层面看，“创建编排”和“创建工程”是并列主路径。
5. 小白用户主要直接使用模板和现成流程；高级用户主要自定义流程和工件结构。
6. 文档工件、表格工件和图形工件共同构成平台输出，不得把平台收缩回单一 Markdown 编辑器。
7. 角色定义必须目录化；输出格式不能定义在角色上，而要定义在工件、节点 IO、阶段输出和导出映射上。

## 2.1 文档约束目标
1. 基线文档不是只为当前协作服务，而是要让另一套 AI 或另一名程序员，在不了解历史对话的情况下，也能做出高度接近的产品。
2. `04-详细需求基线.md`、`05-功能树.md`、`06-功能清单.md` 的目标不是描述方向，而是约束设计。
3. 约束的重点是：
   - 产品定位
   - 主路径与页面层级
   - 对象模型
   - 功能边界
   - 用户动作与系统反馈
   - 状态变化
   - 阻塞条件
   - 输入输出契约
4. 对于 `M/S/A` 级功能，需求、功能树和功能清单必须足以让另一套 AI 100% 复刻相同的功能集合，并复刻高度接近的产品设计。
5. 对于 `B/C` 级功能，允许实现方式和交互细节存在差异，但不得改变信息架构、对象关系和主路径。
6. 如果某项功能在需求、功能树、功能清单中仍然存在多种合理解释，则该项功能不能视为“文档已收口”。

## 3. 完整软件开发流程

### 3.1 需求阶段
1. 先写一句话需求，明确我们要做一个什么软件。
2. 在需求文档中继续向下拆解：
   - 核心功能需求
   - 必要非核心功能需求
   - 使用方式需求
   - 格式范围、输入输出边界
   - 与功能树的映射关系
   - 用户动作
   - 预期结果
   - 失败或阻塞时的系统表现
   - 实现约束与边界
   - 不允许出现的错误实现
3. 需求文档必须先足够清楚，再继续写功能树。
4. 如果需求文档还停留在抽象概念层，视为不可下游拆解。
5. 对于 `M/S/A` 级需求，必须写到“另一个 AI 读完后不会在主路径、对象关系和状态逻辑上做出另一种产品”。

### 3.2 功能定义阶段
1. 依据需求文档建立功能树。
2. 功能树必须体现一级、二级、三级层级关系。
3. 用户可见功能和内部功能都必须进入功能树。
4. 功能树叶子节点必须是最小原子功能单位。
5. 每个原子功能必须带：
   - ID
   - MSABC 分类
   - 当前状态：已完成 / 部分完成 / 未完成
6. 功能树不仅描述“有什么”，还必须描述“从属关系、入口关系、调用关系、阻塞关系”。
7. 对于编排、模板、工件、阶段、角色、导出这类核心对象，功能树必须能看出对象之间的控制关系，而不是只列功能名。

### 3.3 功能清单阶段
1. 功能清单是唯一总表。
2. 每一行都必须对应一个原子功能文档。
3. 任何在方案中出现、但没进入功能清单的能力，视为未正式纳管。
4. 任何在功能清单里标为已完成的功能，都必须有代码和测试证据。
5. 功能清单必须让另一套 AI 看出每个原子功能的：
   - 所属页面或页面集合
   - 所属对象
   - 优先级
   - 当前完成状态
   - 实现文档入口
6. `M/S/A` 级功能若没有足够的页面、状态或对象归属信息，不能进入实现阶段。

### 3.4 UI 设计阶段
1. UI 设计必须围绕功能树展开，不能脱离功能层级单独飘。
2. 每个用户可见页面都必须单独成文。
3. 每个页面文档必须包含：
   - 页面目标
   - 进入与退出
   - 首层显示（小白默认）
   - 深层入口（高手）
   - 布局层级
   - 页面低保真示意图
   - 页面跳转层级图
   - 调用的功能文档
4. 编排相关页面还必须配套“编排层操作与工作方式”文档，说明对象、操作路径和示例 Flow。
5. 页面跳转必须明确区分：
   - 根页面
   - 主内容替换页
   - 工作台子视图
   - 面板/抽屉
   - 对话框/原生选择器

### 3.5 原子功能方案阶段
1. 每个最小原子功能都必须有一个单独文档。
2. 文档目标是：让一个不了解背景的初级程序员或 AI，有 90% 以上概率按文档复原产品。
3. 原子功能文档至少应包含：
   - 基本信息
   - 功能目标
   - 触发与前置条件
   - 调用关系
   - 具体实现方案
   - 自动测试
   - 用户模拟测试
   - 当前审计结论
4. 后续必须继续提高这些文档的实现密度，不允许长期停留在模板化空话层。
5. 对于 `M/S/A` 级原子功能，文档必须写到“另一套 AI 可以做出相同功能效果和相同页面层级”，不能只写技术方向。

### 3.6 Change 阶段
1. 只有当需求、功能树、功能清单、UI 文档、原子功能方案足够清楚后，才允许创建 change。
2. change 的 `proposal/design/tasks` 不能只写概念，必须和原子功能方案一致。
3. 如果一个 change 的 task 未完成，就不能宣称相关能力已经完成。

### 3.7 开发与验证阶段
1. 开发前先核对 action、需求、功能树、功能清单和原子功能方案。
2. 开发时要区分：
   - 已实现
   - 部分实现
   - 未实现
3. 完成判断必须同时满足：
   - 代码主链路存在
   - 自动测试存在且通过
   - 实际运行或手动验证存在
4. 如果没有实际运行程序，只做静态阅读，不得宣称功能就绪。

### 3.8 评审阶段
1. 评审必须从两个视角同时进行：
   - 完备性视角
   - 用户视角
2. 用户视角必须区分：
   - 小白用户的高频路径
   - 高级用户的深层入口
3. 评审结论先标注在当前任务文档中，确认后再直接回写现行基线文档。
4. 评审时不能只看文档里写了什么，还要检查文档没写什么。

### 3.9 合并与归档阶段
1. 同一个内容不要有多个平行文档。
2. 不再长期保留“修复记录/优化记录/补充记录”作为主基线。
3. 评审通过后，再把结论回写到基线文档。
4. 已完成的 change 才允许归档。

## 4. 强制方法规则

### 4.1 不能把方案当实现
1. 类型定义、UI 占位、骨架代码、文档描述，不等于已实现。
2. 任何“看起来像有了”的能力，都必须回到代码和测试主链路核对。

### 4.2 不允许硬编码关键产品能力
1. 模板不能以固定卡片常量的方式写死在 UI 层。
2. AI 提示词、流程和模型选择不能长期写死在代码里作为唯一主路径。
3. 页面层级和交互入口不能靠临时 if/else 拼出来后就当正式设计。
4. 大工程文档管理不能靠“每次全量读全部文档”硬扛，必须建立本地知识底座、混合检索和上下文打包能力。

### 4.3 UI 必须双重服务
1. 首层页面必须为小白降噪。
2. 深层菜单、命令面板、右键菜单、Inspector 高级区必须为高手预留能力。
3. 高频动作必须贴近对象本身。

### 4.4 每次改动都要自问
1. 这个结论是不是我自己的幻觉？
2. 有没有文档、代码、测试或运行证据支持？
3. 我是否真的运行过程序，而不是只看代码？
4. 当前文档是否足够让一个初级程序员独立实现？

### 4.5 MSABC 文档约束标准
1. `M`：没有就无法使用。必须把入口、前置条件、主操作、成功结果、失败结果、恢复路径写死。
2. `S`：核心价值。必须把对象关系、页面层级、状态变化、输入输出契约、可见反馈写死。
3. `A`：重要功能。必须把用户操作、主要反馈、错误处理、与主路径的关系写清楚，允许部分高级交互在原子方案中继续细化。
4. `B`：增强功能。必须写清存在价值、入口位置和不做时的替代路径。
5. `C`：可选功能。必须写清增强点和不影响主路径的前提。
6. `M/S/A` 的共同标准是：另一套 AI 看完需求、功能树、功能清单后，应当能做出几乎相同的产品设计；差异只允许主要落在代码结构和局部交互细节上。

## 5. 本地诊断与会话排障工具

这些工具只服务协作链路排障，不定义产品功能，也不替代测试验收门禁。

| 代码或配置 | 文档对应 | 职责 |
|---|---|---|
| `scripts/codex-link-monitor.sh` | `04-测试验收/03-自动化测试总册.md` 的 Codex 会话与网络诊断命令 | 采集 Codex 会话、网络探针、进程/socket、可选高频采样、可选 TLS key log |
| `scripts/codex-context-pressure-test.sh` | `04-测试验收/03-自动化测试总册.md` 的 Codex 会话与网络诊断命令 | 用合成上下文复现 remote compaction / context pressure 问题，并保存 failure evidence |
| `package.json` 的 `diagnose:codex-*` scripts | `04-测试验收/03-自动化测试总册.md` 的命令表 | 提供统一 npm 入口，方便协作时复现和收集证据 |
| `.gitignore` 中的 `codex.json` 与 `artifacts/` | 本节规则 | 防止本机会话状态、TLS key log、pcap、prompt、rollout 和诊断包进入 Git |

约束：

1. `codex.json` 是本机会话状态，不是项目配置；即使存在也不得提交。
2. `artifacts/codex-link-monitor/`、`artifacts/context-pressure-test/`、TLS key log、pcap、Codex home 日志尾部和 rollout 复制件都是敏感或环境证据，只能本地留存或按需人工脱敏分享。
3. 当 GitHub、ChatGPT、OpenAI 或 Codex remote compaction 出现不稳定时，先使用 `diagnose:codex-link` 或 `diagnose:codex-context-pressure:*` 固化证据，再决定是否继续开发、降级验证或暂停交付。
4. 诊断命令只能解释协作/网络/上下文问题，不能把用户可见功能标记为已完成。

## 6. 当前特殊约束
1. 当前重点先放在编排层和 UI，不再无限扩散话题。
2. 评审意见在确认前不得自动回写到功能树和功能清单，确认后必须回写现行文档。
3. 需求文档必须先把需求拆清楚，再推动下游文档。
