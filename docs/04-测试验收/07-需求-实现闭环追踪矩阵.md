# 07 需求-实现闭环追踪矩阵

## 1. 目标
1. 把“需求 -> 功能树 -> 功能清单 -> UI -> 原子功能方案 -> 开发设计 -> 代码契约与唯一性 -> 实现状态”串成一条可追溯链。
2. 避免某个能力只出现在其中一层文档里，后续开发时再次出现“文档写了、代码没做、测试没测、却误判为完成”。
3. 让另一套 AI 或另一名程序员可以快速判断：某项能力要读哪些文档、写哪些模块、做到什么算完成。

## 2. 使用规则
1. 开发任何复杂能力前，先在本矩阵中定位其 `需求 ID` 和 `功能域`。
2. 若某项能力在本矩阵中没有完整链路，则先补文档，不直接写代码。
3. `实现状态` 以 [06-功能清单.md](../01-需求与PRD/06-功能清单.md) 为准，本矩阵只做追踪，不替代状态总表。
4. 本矩阵优先覆盖 `M/S/A` 能力；`B/C` 能力可以通过功能清单直接追踪。

## 3. 追踪字段定义
- `需求 ID`：来自 [04-详细需求基线.md](../01-需求与PRD/04-详细需求基线.md) 的需求域。
- `功能域`：来自 [05-功能树.md](../01-需求与PRD/05-功能树.md) 的一级/二级域。
- `关键页面`：用户最先感知该能力的页面。
- `原子功能范围`：本域下最关键的原子功能 ID。
- `开发设计`：程序员必须先读的开发设计文档。
- `代码契约与唯一性`：禁止实现分叉的硬约束文档。
- `主实现模块`：未来代码实现时的主模块落点。
- `实现状态`：当前总体状态，只允许 `已完成 / 部分完成 / 未完成`。

## 6. 对初级程序员的使用方式
1. 先根据要实现的功能，在 [06-功能清单.md](../01-需求与PRD/06-功能清单.md) 找到功能 ID。
2. 回到本矩阵，确认它属于哪个需求域和功能域。
3. 按本矩阵给出的 `开发设计 -> 代码契约与唯一性 -> 原子功能文档` 顺序阅读。
4. 若代码实现后无法映射回本矩阵中的链路，则说明实现偏离了当前基线。

## 7. 当前缺口判断
1. 本矩阵能解决“哪个能力应读哪些文档”的问题。
2. 本矩阵不能替代：
   - 原子功能文档
   - 开发设计
   - 代码契约与唯一性
3. 当某行的 `实现状态` 为 `未完成` 时，即便文档完整，也不能视为该能力已在代码中落地。
