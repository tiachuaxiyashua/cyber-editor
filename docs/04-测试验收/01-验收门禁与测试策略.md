# 01 验收门禁与测试策略

## 发布门禁

| 门禁 | 要求 |
|---|---|
| 文档一致 | PRD、产品设计、架构实现、测试验收没有冲突 |
| owner 清晰 | 页面、状态、IPC、服务、持久化、恢复、治理 owner 明确 |
| 用户路径 | 从真实 UI 入口能完成任务 |
| 失败路径 | 阻断、审批、错误、冲突、恢复有测试 |
| 打包态 | 用户可见能力最终使用 `out/package/` 应用验证 |
| 证据 | 记录命令、截图或日志、测试结果和验证项目 |

## 测试层级

1. 单元测试：纯逻辑、状态机、schema、合并策略。
2. 集成测试：IPC、service、持久化、runtime。
3. 用户旅程测试：Playwright 操作真实 UI。
4. 打包态验证：使用 `out/package/` 下可执行应用。
5. 质量评审：检查低级 UI 问题、响应速度、错误提示和证据完整性。

## 不接受的证明

1. 只调用 API，不操作 UI。
2. 只证明组件渲染，不证明用户完成任务。
3. 只测 happy path，不测失败和恢复。
4. 只用开发态 Electron，不做打包态最终验证。
5. 只说“应该可用”，没有命令和证据。

## UI 延迟要求

核心路径必须测试：

1. 页面切换反馈。
2. 节点点击到右侧配置出现。
3. 运行开始到状态显示。
4. 审批生成到待决入口出现。
5. 错误发生到恢复入口出现。
