# 03 自动化测试总册

## 1. 目标

1. 固定 Cyber Editor 自动化测试的执行顺序、覆盖范围和通过标准。
2. 明确每类测试覆盖哪些功能域、调用哪些脚本、产出哪些证据。
3. 让开发者或 AI 在重构前知道最小门禁和增强门禁分别是什么。

## 2. 选择范围

| 测试层 | 默认选择范围 | 配置 |
|---|---|---|
| Vitest 单元测试 | `tests/unit/**/*.test.ts` | `vitest.config.ts` |
| Playwright e2e | `tests/e2e/**/*.spec.ts` | `playwright.config.ts` |
| 合同定义 | `tests/contracts/*.ts` | 由 e2e 合同 spec 和单元守卫读取 |
| 生成测试索引 | `docs/04-测试验收/generated/` | 由 catalog 与 delivery 脚本读取 |

注意：`tests/contracts/*.ts` 是合同定义数据，不是默认直接执行的测试文件；真正执行入口在 `tests/e2e/*contracts.spec.ts` 和部分 `tests/unit/*coverage*.test.ts`。

## 3. 命令分组

### 3.1 基础构建与静态验证

| 命令 | 作用 | 产出 |
|---|---|---|
| `npm run lint` | TypeScript 编译期校验 | `artifacts/test-runs/` 下的报告 |
| `npm run build` | 构建 main、preload、renderer | `.vite/build/` |
| `npm run build:main` | 只构建 Electron main 进程 bundle | `.vite/build/main/` |
| `npm run build:preload` | 只构建 preload bundle | `.vite/build/preload/` |
| `npm run build:renderer` | 只构建 renderer / Vite 前端 bundle | `.vite/build/renderer/` |

### 3.2 单元与文档映射守卫

| 命令 | 作用 |
|---|---|
| `npm run test:unit` | 运行 `tests/unit/**/*.test.ts`，覆盖服务、运行时、边界、文档映射和门禁绑定 |
| `npm run test:unit:watch` | 本地开发时运行 Vitest watch；只作为开发辅助，不作为交付证据 |
| `npm run test:catalog-integrity` | 检查测试编目、质量门禁、UI 合同注册和交付质量门禁的完整性 |
| `npm run test:catalog:execute` | 执行可执行 case catalog，区分 `failed` 与 `unproven`，防止测试假绿 |

### 3.3 Electron e2e 与 UI 合同

| 命令 | 作用 |
|---|---|
| `npm run test:install-browsers` | 安装 Playwright Chromium 依赖，供 e2e 和 UI 合同使用 |
| `npm run test:e2e` | 构建后运行 `tests/e2e/**/*.spec.ts` |
| `npm run test:e2e:headed` | 以 headed 模式运行 Playwright，供本地调试 UI 问题使用 |
| `npm run test:smoke` | 最核心真实流程烟测 |
| `npm run test:ui:shell` | UI 壳层与原型对齐 |
| `npm run test:ui:pages` | 页面几何、布局截图和规则检查 |
| `npm run test:ui:contracts` | 原型、布局、动作、状态、时延、操作和思路地图合同 |
| `npm run test:ui:orchestration` | 关键编排工作流 |
| `npm run test:user-self` | 运行 P018 用户自测脚本，供用户行为路径排障；不替代标准 e2e |

### 3.4 长链路与交付质量

| 命令 | 作用 | 前提 |
|---|---|---|
| `npm run test:post-change-extreme` | 运行极端回归与证据包生成 | 已完成构建 |
| `npm run test:delivery-quality-contracts` | 验证 delivery 类合同 | 已存在 `artifacts/post-change-extreme-validation/` 且包含 export suite |
| `npm run test:delivery-gate` | 交付回归门禁 | 需要按脚本要求生成相关证据 |
| `npm run sync:experience-rules` | 将运行经验同步为规则资产 | 已完成构建；只在需要沉淀经验规则时运行 |
| `npm run demo:closed-loop:regression` | 开发态闭环回归 | 已完成构建 |

### 3.5 打包态验证

| 命令 | 作用 | 前提 |
|---|---|---|
| `npm run package` | 生成 `out/package/.../Cyber Editor.exe` | Windows 打包环境可用，目标 exe 未被占用 |
| `npm run package:win` | 显式按 `win32/x64` 构建打包应用 | Windows 打包环境可用 |
| `npm run package:forge` | 使用 Electron Forge package 入口构建开发包 | 需要 Forge 环境可用 |
| `npm run make` | 生成安装器 | 已完成构建，目标安装器未被占用 |
| `npm run make:win` | 显式按 `win32/x64` 生成安装器 | Windows 打包环境可用 |
| `npm run make:forge` | 使用 Forge make 路径生成 Windows x64 安装器 | 需要 Forge make 环境可用 |
| `npm run test:packaged-smoke` | 打包态冷启动与基础 UI 冒烟 | 已存在打包 exe |
| `npm run test:packaged-project-validation` | 验证 preserved project 可被打包应用打开、重开和校验导出 | 已存在打包 exe 与最近一次 extreme validation 产物 |
| `npm run test:packaged-ui-contracts` | 打包态 handoff/UI 合同 | Windows、打包 exe、post-change extreme artifacts、`CYBER_EDITOR_RUN_PACKAGED_UI_CONTRACTS=1` |
| `npm run test:packaged-closed-loop` | 打包态闭环回归 | 已存在打包 exe 和所需验证项目 |
| `npm run demo:packaged-closed-loop:regression` | 先打包再运行打包态闭环回归 | Windows 打包环境可用，且测试项目按脚本生成 |

### 3.6 发布硬化与质量门

| 命令 | 作用 |
|---|---|
| `npm run review:output-quality` | 审查生成文档和交付物质量 |
| `npm run review:hardcode` | 反硬编码门禁 |
| `npm run scan:release-hardening` | 发布硬化总门禁，串联 lint、unit、build、hardcode、UI、smoke、package、packaged 和 post-change 相关检查 |

### 3.7 Codex 会话与网络诊断

这些命令用于诊断 Codex CLI 会话、远端压缩和 GitHub / ChatGPT / OpenAI 连接链路，不属于产品功能通过证明；诊断产物默认写入已忽略的 `artifacts/`。

| 命令 | 代码入口 | 作用 | 产出 |
|---|---|---|---|
| `npm run diagnose:codex-link` | `scripts/codex-link-monitor.sh` | 采集 Codex 命令转录、DNS/TLS/curl 探针、TCP 443 socket、进程和资源样本 | `artifacts/codex-link-monitor/` |
| `npm run diagnose:codex-context-pressure` | `scripts/codex-context-pressure-test.sh` | 在一个持久 Codex exec 会话中注入合成上下文，复现 remote compaction / context 压力问题；脚本提示模型不得读写仓库 | `artifacts/context-pressure-test/` |
| `npm run diagnose:codex-context-pressure:no-compression` | `scripts/codex-context-pressure-test.sh` | 关闭 request compression 后跑同一压力测试，用于对比压缩开关影响 | `artifacts/context-pressure-test/` |
| `npm run diagnose:codex-context-pressure:tui` | `scripts/codex-context-pressure-test.sh` | 使用 TUI driver 和伪终端复现非 exec 路径问题 | `artifacts/context-pressure-test/` |
| `npm run diagnose:codex-context-pressure:monitor` | `scripts/codex-link-monitor.sh` + `scripts/codex-context-pressure-test.sh` | 将链路监控、1 秒普通采样、0.25 秒高频采样、Codex home 日志尾部和 TLS key log 与压力测试组合起来 | `artifacts/codex-link-monitor/` 和 `artifacts/context-pressure-test/` |

使用约束：

1. `--tail-codex-home` 可能采集本机 Codex 日志正文，`--tls-keylog` 会生成可用于解密匹配 pcap 的 TLS 会话密钥；二者只能作为本地排障证据，不得提交。
2. `scripts/codex-context-pressure-test.sh` 生成的 prompt、rollout、TLS key log 和 failure evidence 只用于诊断远端压缩问题，不得作为产品测试绿灯。
3. 这些命令可以解释“为什么本轮无法继续协作或验证”，但不能替代 `test:unit`、`test:e2e`、packaged smoke 或 post-change evidence。

## 6. 重构前最小门禁

通用重构至少运行：

1. `npm run test:catalog-integrity`
2. `npm run test:unit`
3. `npm run test:smoke`

改到页面结构或 UI 合同时追加：

1. `npm run test:ui:pages`
2. `npm run test:ui:contracts`

改到交付、导出、长链路时追加：

1. `npm run test:post-change-extreme`
2. `npm run test:delivery-quality-contracts`

改到 packaged、重开工程或 handoff 时追加：

1. `npm run package`
2. `npm run test:packaged-project-validation`
3. `npm run test:packaged-ui-contracts`

## 7. 证据位置

| 证据 | 位置 | 说明 |
|---|---|---|
| 测试报告 | `artifacts/test-runs/` | 由命令包装器生成 |
| 生成测试索引 | `docs/04-测试验收/generated/` | 测试用例、覆盖率和质量门禁索引 |
| post-change 证据 | `artifacts/post-change-extreme-validation/` | 运行 `test:post-change-extreme` 后产生 |
| delivery / closed-loop 证据 | `artifacts/` 下对应脚本目录 | 运行相关脚本后产生 |
| 打包产物 | `out/package/` | 运行 `npm run package` 后产生 |
| preserved verification project | `out/manual-projects/` | packaged handoff 使用的人工可重开项目 |

当前没有运行过对应命令时，不得把这些目录写成已经存在的证明。

## 8. 自动化测试 Oracle

1. `M` 级功能必须有自动化测试，并至少覆盖一个失败或恢复路径。
2. `S` 级功能必须有单测或 e2e；涉及多层联动时必须有 e2e。
3. `A` 级功能至少要有单测、e2e 或被更高层闭环测试间接覆盖，并在原子文档中明确写出。
4. 若自动化测试不存在，只能标记为 `部分完成` 或 `未完成`，不能标记为 `已完成`。
5. 若 suite 通过但 case catalog 标记为 `unproven`，不得把对应用户能力判定为已证明。

## 9. 完成定义

只有当以下 4 项同时成立时，才能说某个功能域通过自动化验证：

1. 该功能域对应命令全部执行成功。
2. 对应测试或脚本全部通过。
3. 对应产出物或证据文件真实存在。
4. [06-功能清单.md](../01-需求与PRD/06-功能清单.md) 中的状态与测试结果一致。
