# 24 AI 运行时细化状态机

## 1. 目标
1. 固定 AI 会话、阶段控制、模型路由和结构化生成的状态变化。
2. 防止不同实现者在“什么时候能发送、什么时候能确认、什么时候写工件、失败时怎么回退”上做出不同系统。

## 2. 会话输入状态机
```text
composer_idle
  -> composer_typing
composer_typing
  -> composer_ready
composer_ready
  -> submitting
submitting
  -> composer_idle
  -> composer_error
composer_error
  -> composer_typing
```

约束：
- `composer_ready` 前至少满足：非空、当前会话存在、当前 provider 可用。
- `submitting` 期间发送按钮不可重复触发同一条消息。

## 3. 单次运行状态机
```text
accepted
  -> planning
planning
  -> routing
routing
  -> running
running
  -> structured_validating
  -> failed
  -> stopped
structured_validating
  -> repairing
  -> succeeded
  -> failed
repairing
  -> succeeded
  -> failed
failed
  -> retry_ready
retry_ready
  -> accepted
```

约束：
- `routing` 必须记录命中模型和命中原因。
- `structured_validating` 只在该 run 需要结构化结果时出现。
- `repairing` 必须是显式步骤，不允许把修复隐藏在成功路径里。
- `retry_ready` 必须保留原错误，不得覆盖失败 run。

## 4. Provider 命中状态机
```text
provider_unknown
  -> provider_diagnosing
provider_diagnosing
  -> provider_ready
  -> provider_unavailable
provider_ready
  -> provider_selected
provider_selected
  -> provider_routed
provider_unavailable
  -> provider_retesting
provider_retesting
  -> provider_ready
  -> provider_unavailable
```

约束：
- 用户选中 profile 后必须自动进入 `provider_selected`。
- `provider_routed` 必须显示本次实际命中的模型，而不是只显示配置名。

## 5. 阶段 Guard 状态机
```text
guard_unknown
  -> guard_checking
guard_checking
  -> guard_ready
  -> guard_blocked
guard_blocked
  -> guard_checking
guard_ready
  -> confirm_attempt
confirm_attempt
  -> confirmed
  -> guard_blocked
```

约束：
- `guard_checking` 必须同时检查：
  - 输入完整性
  - 阶段必需工件
  - blocker 数量
  - 最近关键运行结果
- `guard_ready` 只是本地可确认态；真正确认前主进程必须再次校验。

## 6. 阶段草稿生成状态机
```text
draft_idle
  -> draft_guard_checking
draft_guard_checking
  -> draft_blocked
  -> draft_running
draft_running
  -> draft_artifact_writing
  -> draft_failed
draft_artifact_writing
  -> draft_succeeded
  -> draft_failed
```

约束：
- `draft_running` 不得直接把聊天文本当工件。
- `draft_artifact_writing` 后必须刷新工件状态、阶段状态和文档区。

## 7. 审查子流程状态机
```text
review_idle
  -> blue_running
blue_running
  -> red_running
red_running
  -> judge_running
judge_running
  -> review_blocked
  -> review_passed
  -> review_continue
review_continue
  -> blue_running
```

约束：
- 蓝军、红军、裁判必须是独立 run 或独立节点状态，不允许合并成一段不可分辨的文本。
- `review_continue` 必须带轮次号。

## 8. 结构化生成状态机
```text
text_only
  -> structured_requested
structured_requested
  -> schema_validating
schema_validating
  -> schema_passed
  -> schema_failed
schema_failed
  -> repair_requested
repair_requested
  -> schema_validating
  -> failed
```

约束：
- 结构化结果必须有明确 schema。
- `schema_failed` 后不得直接假装成功并写工件。

## 9. 错误实现示例
1. Guard 不通过时仍允许确认阶段。
2. Provider 诊断失败后依然把消息发送出去，最后才报错。
3. 结构化生成失败后把原始脏文本直接写入工件。
4. 重试时覆盖旧 run，导致历史不可追溯。
