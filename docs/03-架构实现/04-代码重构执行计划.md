# 04 代码重构执行计划

## 目标

把当前工程从“大文件集中装配 + 多域逻辑混杂”收口为可维护、可测试、可扩展的桌面工作台架构。

## 当前热点

1. `src/renderer/App.tsx`：5182 行，壳层、路由、对话框、状态装配过于集中。
2. `src/renderer/components/OrchestrationWorkspace.tsx`：5422 行，画布、Inspector、治理、运行控制耦合过高。
3. `src/main/services/runtime-service.ts`：4158 行，运行状态机、审批、rerun、恢复集中在一个 owner。
4. `src/main/services/project-service.ts`：1594 行，工程、文档、工件、审计边界混合。
5. `src/shared/types.ts`：2007 行，跨域类型过度聚合。
6. `src/renderer/styles.css`：7145 行，全局样式影响面过大。

## 第一阶段：文档与入口收口

1. 以当前 `docs/` 为唯一文档体系。
2. 让 `03-架构实现/` 能直接对照 `src/` 当前目录和 owner。
3. 删除旧根目录镜像与历史索引，只保留 `06-详细设计库/` 内的细节材料。
4. 任何后续改动先对照 PRD、产品设计、架构、测试验收。

## 第二阶段：Renderer 拆分

### 2.1 `App.tsx`

目标拆分：

| 目标 owner | 责任 |
|---|---|
| `AppShell` | 全局布局、活动视图、状态条、窗口级装配 |
| `WorkbenchRouteController` | 欢迎页、工程视图、搜索视图、设置视图切换 |
| `ConversationWorkspace` | 会话区、阶段区、上下文面板 |
| `ResourceWorkspace` | 资源中心、模板/技能/角色入口 |
| `DocumentWorkspace` | 文档、表格工件、AI 写回和冲突入口 |

### 2.2 `OrchestrationWorkspace.tsx`

目标拆分：

| 目标 owner | 责任 |
|---|---|
| `FlowCanvasWorkspace` | 画布、节点、边、拖拽、布局 |
| `NodeInspector` | 节点配置与对象级编辑 |
| `RuntimeControlRail` | 当前 run、pause/resume/retry/stop |
| `GovernanceRail` | 审批、阻断、治理与证据入口 |
| `AssetEditors` | 角色、连接、工具、契约、导出映射 |

## 第三阶段：Main Service 拆分

### `runtime-service.ts`

优先拆出：

1. `RunStateMachine`
2. `ApprovalCoordinator`
3. `RerunPlanner`
4. `RecoveryCoordinator`
5. `RuntimeEvidenceWriter`

### `project-service.ts`

优先拆出：

1. `ProjectBootstrapService`
2. `DocumentWorkspaceService`
3. `ArtifactWorkspaceService`
4. `ProjectAuditService`

### `types.ts`

按领域拆分为：

1. `project.types`
2. `document.types`
3. `runtime.types`
4. `resource.types`
5. `rules.types`
6. `evidence.types`

## 第四阶段：复杂闭环补强

1. 并行分支运行和汇合冲突。
2. 循环节点和退出条件。
3. 子流程输入输出契约。
4. 断点恢复和重启继续。
5. 工件失效传播和局部重跑。
6. AI 写回冲突合并。
7. 思路地图、知识索引、规则沉淀的真实闭环。
8. 资源导入与副作用审批的证据闭环。

## 第五阶段：测试与打包态验收

1. 保持 `tests/unit/` 对 service 边界、治理和契约的覆盖。
2. 保持 `tests/e2e/` 对工作台、编排、审批、知识索引、规则沉淀、思路地图的主路径覆盖。
3. 所有用户可见验收最终使用打包应用。
4. 发布前必须产出 `artifacts/` 与 `out/package/` 的证据路径。
