# 04 代码重构执行计划

## 目标

把当前工程从“大组件 + 分散运行逻辑”收口为可维护、可测试、可扩展的工作台架构。

## 第一阶段：文档和规则收口

1. 以当前 `docs/` 为唯一文档体系。
2. 全局规则指向新的文档入口。
3. 任何后续代码修改先读 PRD、产品设计、架构实现和测试验收。

## 第二阶段：UI 主路径收口

1. 重做编排页首屏：画布最大，右侧直接编辑节点。
2. 新增或收口阶段条、运行条、待决入口、恢复卡。
3. 移除关键动作对隐藏流程面板、命令面板和运行弹层的依赖。
4. 替换高风险 `window.confirm` 为结构化审查界面。

## 第三阶段：代码 owner 拆分

优先拆分：

1. `App.tsx`
2. `OrchestrationWorkspace.tsx`
3. `runtime-service.ts`

拆分目标：

| 新 owner | 责任 |
|---|---|
| AppShell | 全局布局、导航、工作区装配 |
| WorkbenchRouteController | 页面路由和工程上下文 |
| DocumentWorkspace | 文档编辑和 AI 写回 |
| OrchestrationWorkspace | Flow 画布和节点选择 |
| NodeInspector | 节点配置 |
| RunStatusStrip | 运行状态和控制 |
| DecisionInbox | 审批、冲突和待决事项 |
| RuntimeService | run、node、checkpoint、事件 |
| ArtifactService | 工件写入、版本和失效传播 |
| EvidenceService | 来源、审计和追溯 |

## 第四阶段：复杂任务闭环

1. 并行分支运行和汇合冲突。
2. 循环节点和退出条件。
3. 子流程输入输出契约。
4. 断点恢复和重启继续。
5. 工件失效传播和局部重跑。
6. AI 写回冲突合并。
7. 证据追溯和质量评分。

## 第五阶段：测试和打包态验收

1. 增加核心旅程 UI 延迟测试。
2. 增加编排、审批、恢复、写回冲突的用户行为测试。
3. 所有用户可见验收最终使用打包应用。
4. 发布前必须产出证据路径。
