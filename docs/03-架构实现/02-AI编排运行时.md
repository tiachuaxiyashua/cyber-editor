| 对象 | 当前代码 owner | 说明 |

| Flow | `ConversationFlowService`, `RuntimeAssetService`, `OrchestrationWorkspace.tsx` | 用户设计或由自然语言生成的流程资产 |

| Run | `RuntimeService` | 一次 Flow 执行，包含状态、事件、审批、恢复与 rerun 信息 |
| Approval | `RuntimeService`, `SideEffectGovernanceService` | 运行中的人工确认，或副作用执行前审批 |

## 智能体编排对象分层

这里的“分层”不是 Electron / IPC / Service 代码目录分层，而是 AI 编排运行时的对象职责分层。当前代码的基本关系是：

```text
用户目标 / 工程上下文
  -> 工作流 Workflow / RuntimeTemplateAsset：定义阶段、默认 Flow、阶段角色、阶段工件、导出映射
  -> 编排层 Flow / Node / Edge：定义节点、边、IO、控制流、调试与局部重跑入口
  -> 角色 Role / RolePackage / RoleProfile：定义谁来做、按什么身份和原则做、默认技能与能力边界
  -> 技能 Skill：提供可注入的能力说明、方法约束和复用知识
  -> 智能体 Agent Runtime Instance：运行时临时合成的执行者
  -> RuntimeService：选择模型、组装上下文、执行节点、调用能力、持久化 run / event / evidence
  -> 产物：message / control signal / artifact / evidence / run state
```

一句话边界：工作流决定“大阶段和交付壳”，编排决定“怎么流转”，角色决定“谁来做”，技能决定“会什么方法”，智能体是运行时由角色、任务、节点和上下文临时合成出来的执行实例。

### 1. 工作流层：Workflow / RuntimeTemplate

| 维度 | 当前定义 |
|---|---|

| 不能做 | 不能替代 Flow 的节点级控制流；不能把角色人格、技能正文、工具执行细节写进阶段配置；不能绕过 guard、审批、写回治理 |
| 输入 | 模板包、工程状态、当前阶段、阶段工件、用户触发动作 |
| 输出 | 阶段要求、默认 Flow 入口、阶段角色选择、阶段工件要求、导出映射、guard/review 所需上下文 |

## 运行流转机制

### 设计态流转

```text
模板包 / 空白工程
  -> PlatformService 初始化或读取 .project/platform/
  -> OrchestrationWorkspace 展示 Flow、Subflow、Role、Connector、Tool、TaskTemplate、AgentProfile
  -> 用户拖拽节点、连线、绑定角色/任务/技能/工具、配置 IO
  -> validatePlatformFlow 校验结构、引用、节点语义和工件契约
  -> PlatformService.saveFlow / saveRoles / saveTaskTemplates / saveAgentProfiles 落盘
```

设计态的唯一真相是平台资产：`.project/platform/` 下的 Flow、Subflow、Role、TaskTemplate、AgentProfile、Connector、Tool。Renderer 只保存草稿和反馈，不直接成为长期真相源。

### 运行态流转

```text
用户运行 Flow / 调试节点
  -> RuntimeService.ensureProjectRuntime()
  -> 读取 PlatformAssets 与 RuntimeTemplate
  -> validatePlatformFlow() + 工件契约校验
  -> agent 节点：resolveRoleBundle()
       RolePackage / PlatformRole
       + TaskTemplate
       + AgentProfile
       + Node Binding(skill/tool/connector/model)
       -> EffectiveExecutionBundle
  -> readSkillInstructionsSafe(effectiveSkillIds)
  -> buildHarnessPrompt() + buildContextPack()
  -> ModelRouter.select()
  -> StructuredGenerationService.generateText()
  -> 可选：CapabilityRuntime.execute() 受控能力调用
  -> RuntimeOutputRecord / RuntimeArtifactOutcome / checkpoint / event
  -> EvidenceStoreService.persistContextPack() / persistRunEvidence()
  -> RuntimeAssetService.saveRun() / saveRunHistory() / saveRunRecovery()
  -> UI 刷新 run 状态、节点状态、阻塞项、工件和审批入口
```

### 审批与中断流转

```text
approval 节点或副作用请求
  -> RuntimeService / SideEffectGovernanceService 创建 pending approval
  -> run.status = waiting-approval，recovery.status = recoverable
  -> UI 展示批准 / 拒绝
  -> resolveRuntimeApproval()
       approved: 写 final output、checkpoint、approval.approved event、run completed/resolved
       rejected: run stopped、errorMessage、checkpoint failed、approval.rejected event
```

### 工具与能力流转

```text
模型输出严格 toolCalls JSON
  -> RuntimeService 校验 capabilityAllowed()
  -> CapabilityRuntime.execute()
  -> 内置能力 / connector / script tool
  -> script tool 通过 PlatformService.runTool()
  -> 工具结果回灌给下一轮模型或生成 final output
  -> 未授权能力写 permission.blocked event，不执行
```

### 产物类型边界

| 产物 | 用途 | 当前落点 / 表达 |
|---|---|---|
| message | 节点间临时沟通，不保证成为最终交付物 | `inputMessageKeys`, `outputMessageKeys`, run output |
| control / signal | 条件、循环、并行、审批和边流转控制 | `PlatformFlowEdge.branch`, `outputSignalKeys`, 节点状态和 run event |
| artifact | 正式输入、中间产物或最终交付物 | `inputArtifactPaths`, `outputArtifactPaths`, `artifactPath`, 工件文件和治理记录 |
| evidence | 可审计证据，不是交付正文 | context pack evidence、run evidence、approval/side-effect evidence |
| run state | 运行状态、恢复点和历史 | `.project/runtime/` 下的 run、history、recovery、event |

## 运行语义

1. Flow 运行必须生成 `runId`，并由 `RuntimeService` 写入事件与恢复状态。
2. 节点进入、完成、失败、跳过、重试、等待审批、需要合并都必须形成可见状态。
3. 人工确认不是 UI 假动作，必须落到 `pendingApprovals` 与证据存储。
4. 局部重跑必须先生成预览，再允许真正应用。
5. 工件写入不能只写文件，还必须更新工件治理、证据与失效传播。
6. 思路地图不是演示层，必须能从真实会话与证据投影出来，并保存布局。
7. 规则沉淀、知识索引和上下文包必须能在当前工程上重复生成，而不是一次性 UI 数据。

## AI 写回与治理

AI 写回文档或工件前必须展示：

1. 修改目标。
2. 变更 diff。
3. 来源消息、阶段或节点。
4. 影响范围。
5. 冲突状态。
6. 接受、拒绝、局部接受、手动合并。
7. 回滚或快照恢复方式。

本地副作用和远程资源导入必须经过：

1. `ResourceGovernanceService` 或 `SideEffectGovernanceService` 的预览/校验。
2. 审批记录或 review gate 结果写入证据。
3. UI 中可见的批准、拒绝或阻断反馈。

## 证据追溯

每个可交付输出至少应能追溯到：

1. 用户输入或触发命令。
2. 使用的上下文包和索引状态。
3. 模型、Provider 与结构化生成链路。
4. 执行节点与 run 事件。
5. 审批记录或副作用批准。
6. 写回 diff、工件版本或导出结果。
7. 对应测试或运行证据路径。

## 失败恢复

当前失败恢复必须能回到以下入口：

1. 运行控制条上的暂停、恢复、停止、重试。
2. 审批节点的批准/拒绝。
3. rerun 预览后的局部重跑。
4. 文档快照与冲突合并。
5. 思路地图布局重置。
6. 资源导入与副作用的 review gate / approval 结果。
