# 2026-04-29 文档集梳理与代码对照报告

## 1. 结论

当前文档已经能描述“以编排层为核心的桌面图文工作台”这个目标，但距离用户期望的完整效果仍是部分达成。

能够达成的部分：

1. 产品定位、双主入口、文档工作台、编排工作台、AI 会话、模板体系、知识底座和测试治理已经形成单一文档体系。
2. `docs/` 能按“需求 -> 产品设计 -> 架构 -> 详细设计 -> 测试验收 -> 代码对照”的顺序指导开发。
3. 当前代码确实存在对应主链：React/Electron Renderer、preload IPC、main services、`.project/runtime`、测试证据和打包脚本。

尚不能完全达成的部分：

1. 许多核心能力仍是 `部分完成` 或 `未完成`，尤其是无工程编排、完整 Flow 编辑语义、角色包实例化、工件契约、模板生命周期、远程资源 UI 和完整打包态证据。
2. 文档中部分旧接口表、代码规模数字和测试追踪矩阵没有及时对齐代码。
3. 部分测试 Oracle 仍保留“See canonical oracle”等弱摘要，不足以独立证明每个 case 的可执行 oracle。

## 3. 当前方案主要缺陷

### 3.1 产品完成度缺陷

1. 无工程编排仍未闭环：`F-005`、`F-060`、`F-061`、`F-064`、`F-069`、`F-070`、`F-075` 到 `F-077`、`F-084`、`F-086` 仍未完成。
2. 自然语言编排已具备 plan/draft/patch 主链，但 `F-125` 到 `F-127` 仍缺少逐项接受、完整角色/工件目录输出合同和运行态阻断证据。
3. 远程角色包已具备 service 与 IPC 能力，但 `F-128` 缺少编排页角色资产区真实 UI e2e 证据。
4. `F-129` 目前只有 `GStack Office Hours` 默认模板和参考分析，不能等同于完整 `GStack 软件交付工作流模板`。

### 3.2 架构与实现缺陷

1. `App.tsx`、`OrchestrationWorkspace.tsx`、`styles.css`、`runtime-service.ts`、`types.ts` 和 `project-service.ts` 仍是过大热点文件。
2. `src/shared/types.ts` 聚合了过多跨域类型，长期会拖慢模块边界收敛。
3. IPC 已经较完整，但仍依赖 `preload.ts` 人工维护，缺少从 preload 自动生成接口文档的机制。
4. 知识检索当前的 semantic 是 token overlap，不是向量检索；文档不得宣称已经完成真正向量语义检索。

### 3.3 测试与证据缺陷

1. 许多 `M/S/A` 能力在测试矩阵中有路由，但没有 case-level oracle proof。
2. `docs/04-测试验收/11-MSA-test-oracle-matrix.md` 仍有弱摘要行，需要后续逐项改成可执行断言。
3. 打包态验证不是所有用户可见能力的最终证明路径，当前只能证明部分 smoke/UI 合同。
4. `scripts/audit_doc_governance.py` 仍按旧文档结构查找文件，当前不应作为可信治理脚本使用。

## 4. 是否能达到用户想要的效果

按当前文档和代码，能达到“方向正确、核心底座存在、局部路径可用”的效果；还不能达到“完整软件工厂式自动编排、全量可视 Flow 设计、稳定角色/技能/模板市场、全链路打包态可证明”的最终效果。

要达到目标效果，优先顺序应是：

1. 收口无工程编排和 Flow 保存/运行态。
2. 补齐 Flow 画布拖拽、连线、并行、循环、子流程和面板布局。
3. 补齐自然语言编排的逐项 patch、角色/工件目录合同和运行态阻断。
4. 补齐模板生命周期、GStack 软件交付模板和从模板直接开始编排。
5. 补齐角色包远程安装的真实 UI 路径。
6. 把 `11-MSA-test-oracle-matrix.md` 的弱 oracle 摘要逐步替换成可执行断言。

## 5. 后续建议

1. 不要再新增平行文档目录；所有长期内容继续回写到 `docs/` 当前结构。
2. 每次新增 `F-*` 或 `INF-*` 必须同步功能树、功能清单、MSA 矩阵、测试映射和详细设计 README。
3. 修复 `scripts/audit_doc_governance.py`，让它按当前 `docs/01-需求与PRD/06-功能清单.md` 与 `docs/04-测试验收/11-MSA-test-oracle-matrix.md` 工作。
4. 后续判断“已完成”时继续坚持：文档一致、代码 owner、用户路径、测试证据、打包态证明五项同时满足。
